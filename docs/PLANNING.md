# 主动规划与人机决策

本轮对应能力全景 C03，以及 C05 的问题/计划决定、C12 的规划只读边界。用户批准后实现，验收证据在本文末尾维护；这不是 G02—G04 的候选性能比较。

## 1. 用户流程与权限

新建和追加消息都提供“自动 / 先规划”。自动模式允许 Agent 根据复杂度主动调用规划工具；简单任务可以沿用原执行方式。选择“先规划”会从运行开始限制项目写入与命令。需要每个任务都先批准时，在宿主运行 TOML 设置：

```toml
planning_policy = "required"
```

宿主默认 `auto`，浏览器不能覆盖 `planning_policy`。`required` 在 CLI/Web 共用的 Runner 内生效，自动入口也不能先执行命令再补规划。项目 AGENTS.md 的自然语言规则仍交给模型理解；需要确定性的限制，应使用先规划入口或宿主强制策略。

完整流程是：读取项目 → 必要时提问 → 回答后继续研究 → 提交方案 → 批准/要求修改/拒绝 → 执行与测试 → 查看代码、检查和计划进度。批准范围内持续完成实现、测试与必要修复；范围明显变化时，Agent 重新进入规划并提交新版本。

规划阶段允许 `list_files`、`read_file`、`search_files`、受控 `read_context` 和规划工具。写文件、局部编辑和所有 `run_command` 都由后端拒绝，包括声称“只读”的命令；宿主项目测试也不会运行。目录发现使用只读列表，不需要 Shell。该约束只作用于 Harness 工具调度，不是操作系统命令沙箱，也不阻止用户或其他本机进程自行修改项目。

## 2. 模型可调用的工具

| 工具 | 输入与结果 | 宿主行为 |
| --- | --- | --- |
| `enter_plan_mode` | `reason` 说明复杂度、重大选择或范围变化 | 进入只读规划，撤销旧版执行授权；不会请求用户再次批准“进入规划”本身 |
| `ask_user_question` | 自包含 `question` 和最多6项建议 `options`；允许自由回答 | 保存问题并等待，后续同批工具不执行；没有默认答案或超时批准 |
| `submit_plan` | `title`、目标架构 `summary`、`scope`、`steps`、`verification` | 创建新版本，绑定实际目录及对象身份，进入待批准；提交本身不授予权限 |
| `update_plan` | 当前 `version`、一基 `step` 编号、进度 `status` | 只能更新已批准方案的已有步骤；最多一个步骤进行中；完成进度不等于独立检查通过 |
| `read_plan` | `section=plan/history/decisions`、可选版本、字节偏移及正文指纹 | 只读当前或旧版完整方案、版本目录和决定原文；默认每页4096字节，最多16384，跨页内容变化时要求重读 |
| `list_files` | 工作区 `directory`、零基 `offset`、每页 `limit` | 只读列举直接子项；不跟随链接或junction，不公开运行记录；最多扫描10000项，跳过或截断明确标记 |

四个状态控制工具和一个 `read_plan` 只读工具由宿主绑定后统一提供，不放进网页文件工具复选框；`list_files` 随文件读取能力提供。所有声明和实际规划阅读视图都参与真实模型输入预算，没有额外的无限上下文。

## 3. 状态、持久化与接续

计划的事实源为结构化运行记录。配置的运行根目录下，每个 `<run_id>/run.json` 固定初始 `planning`，`events.jsonl` 保存完整规划变更和终态；`summary.json` 仅为终态缓存，损坏或不一致时以事件日志为准。会话索引连接各轮，计划版本和用户决定随可信运行记录保留。源码默认根目录为项目 `.runs`；当前 Windows 桌面发布配置默认使用 `D:\Codex\AgentHarness\runs`，可通过宿主启动参数指定其他位置。页面可以导出 Markdown 派生快照，但没有另设可编辑的 Markdown 事实源，不替代批准记录。

`RunManifest.planning` 保存本轮开始时的模式、计划版本、待处理请求和用户决定。工具状态变化先提交 `planning_updated` 事件，再发布内存状态；保存失败时停止后续动作。`RunResult.planning` 固定本轮结束状态，旧轮记录不随新轮变化。

提问或提交计划后，本 Run 以 `waiting_input` 结束并释放现有单执行槽。此状态不是开发完成，也不执行验收。人类等待时间不占用一个存活的模型请求或运行超时；用户回答或批准后，使用现有幂等 followup 协议建立新 Run，继承历史、当前代码和批准事实，并获得独立预算。这是逻辑任务的跨轮接续，不是从旧协程的指令位置精确恢复。

刷新和服务重启只读取状态。缺少终态时，从可信的输入和最后一个完整规划事件重建请求，并按既有中断接续协议处理未知工具结果，不重放动作。普通目录保持原目录，隔离会话保持同一工作树；原有代码差异、产物与下载快照规则不变。

## 4. 用户决定与防重复

`POST /api/runs/{latest_run_id}/followups` 继续复用 `request_id`。问题和计划操作额外携带 `decision`：

```json
{
  "request_id": "浏览器生成的UUID",
  "prompt": "批准执行计划 v1",
  "decision": {
    "interaction_id": "当前请求UUID",
    "action": "approve",
    "plan_version": 1
  }
}
```

问题接受 `answer` 或 `cancel`，`plan_version` 必须为空；计划接受 `approve`、`revise` 或 `reject`，必须匹配当前版本。没有注册模型可调用的批准工具。普通消息可回答当前问题；待批准时普通消息按修改意见处理，单独输入“批准”不会解锁，页面提供明确的“批准并执行”按钮。

宿主同时核对会话最新轮、请求编号、方案版本、目录路径及对象身份。重复相同请求返回原 Run；相同编号不同内容、旧版本、旧问题和非最新父轮均拒绝。拒绝计划或取消问题只保存决定和完整历史，不调用模型、工具或测试。迟到答复不会自动恢复已经取消的请求，后续工作须由用户发起新消息。

首版限制每会话最多30个方案版本、100条用户决定；超限明确要求新建会话。方案正文不能通过进度工具修改。批准的是记录中的方案及工作区，不提供对自然语言范围的形式化证明；实际工具和命令仍受原有配置、路径边界和运行预算约束。

## 5. 前端与CLI

会话内显示问题、可选答案及自由输入，提供回答/取消等待；方案展示版本、目标架构、范围、步骤、验收和工作区，提供批准/修改/拒绝。发送不确定时保持原请求，只能重试确认，不重新生成批准请求。历史检查器只读，各版本与用户决定可以回看。

计划界面参考 Codex 对规划方案与执行清单的区分，采用会话内计划块。待批准时展开完整方案；正文有独立的阅读滚动区，批准操作位于区外。批准后默认收起长文，展示完成步骤数、进度和当前进行中/受阻步骤，可随时展开全文。编号清单对应固定步骤，颜色与图标之外保留可读状态。修改意见只在点击“要求修改”后展开，返回审阅保留草稿，提交修改前不产生决定；切换请求清空旧答案。历史版本、决定记录及执行目录按需展开。前端仅在最新展示版本与待批准请求匹配时提供操作，真正的授权核验仍由宿主负责。

该轮只调整前端呈现与交互，不改变后端接口、计划数据结构、只读策略、事件事实源或预算。主页面和历史检查器复用同一组件；相关联动通过真实后端的离线响应测试及浏览器点击链路验收。参考：[Codex 规划模式](https://learn.chatgpt.com/docs/developer-commands?surface=cli#switch-to-plan-mode-with-plan)、[结构化 update_plan 工具](https://developers.openai.com/cookbook/examples/gpt-5/codex_prompting_guide#update-plan)、[长任务 Markdown 计划](https://developers.openai.com/cookbook/articles/codex_exec_plans)。这是本项目的界面适配，不声明逐像素复刻 Codex 桌面端。

列表区分等待回答、等待批准、规划结束和拒绝计划；不会把这些控制流程展示成代码已验收。计划步骤是模型进度陈述，测试和独立验收保留自己的事实来源。

CLI 共用规划工具、强制策略和记录。等待输入返回码为4，输出当前问题/计划；CLI 尚无交互式回答/批准命令，完整交互首版在网页登记会话内提供，不能承诺 CLI 创建的无来源记录能通过网页直接接续。

本轮没有加入运行中任意纠偏、暂停恢复、任务队列、并发调度、独立 Agent Tasks、Subagents 或通用动作审批。这些继续按能力全景安排。

### 7.1 模型的阅读视图

每次执行请求在计量之前，从可信控制器重新注入最新单版计划，包含完整目标架构、范围、步骤、验收和状态；保留版本数、决定数，不注入历史正文、目录对象身份或决定原文。当前计划本身仍占输入预算，无法装入时按既有上限停止，不静默截断重要约束。压缩摘要只整理旧工作记录，之后的执行请求再次使用宿主最新状态，不能由摘要重写批准事实。

成功的进入规划、提交方案、更新进度操作已由当前状态表达，工具回执只返回版本、状态和等待类型；模型输入不重复携带这些成功调用的历史正文。原始事件、消息及索引完整保留。混合工具批次仅在阅读投影中移除对应调用及结果，保持其余配对；失败结果、问题及用户回答、显式 `read_plan` 回读均保留。问题不能被当作过期进度省略，避免用户回答“JSON”后失去问题对象。

`read_plan` 的 `section` 为 `plan`、`history` 或 `decisions`：单版全文、版本目录、决定原文。`version=None` 默认最新，其他分区必须省略版本。返回 JSON 正文的 UTF-8 安全分片、`next_offset`、`eof`、总字节数和 `sha256`；跨页传回 `expected_sha256`，记录变化时重新从第一页读取。没有任意会话、文件路径或批准参数。只读查询不产生 `planning_updated`；回读内容仍参与工具及输入预算，并避免刚读出的页面被立即外置成引用。

### 7.2 人工阅读与下载

当前计划和历史版本各有 Markdown 导出入口，运行检查器也能导出当轮快照。入口绑定 `runId + version`，不随最新轮变化。附件地址复用 `GET /api/runs/{run_id}/artifacts?location=run&path=plans%2FvN.md`；服务仅接受该轮确实存在的版本，目录穿越及任意记录文件仍拒绝。

Markdown 包含版本、当轮批准状态、执行目录、完整正文、步骤和验收方式。它是派生快照，编辑下载文件不会改变宿主批准状态。需要进入 Git 时，用户可将文件保存到项目 `docs/plans/`。导出不写项目、不创建 Run、不调用模型或工具，也不替用户批准。

派生缓存位于 `<run_id>/.plan-exports/<正文sha256>/plan-vN.md`，相同内容复用，进度变化生成新内容目录，旧来源不被覆盖；目录链接和缓存篡改明确拒绝。网页采用浏览器附件下载；桌面沿用统一原生附件入口与已配置下载目录，无需新增 IPC 或第二条下载协议。正式事实源仍为 `run.json`、`events.jsonl` 及其终态缓存。
