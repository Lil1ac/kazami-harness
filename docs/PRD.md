# Agent Harness 产品需求文档

- 文档版本：0.5
- 更新日期：2026-10-20
- 状态：产品需求基线；实施进度统一见 [项目概览](../PROJECT.md)
- 产品工作名：Agent Harness
- 当前交付重点：真实项目的小修改、项目测试证据与用户代码审阅
- 配套设计：[V0.1 技术设计](TECH_DESIGN_V0.1.md)
- 前端交付要求：[前端运行控制台](FRONTEND_REQUIREMENTS.md)（基础控制台已实现，后续能力继续同步交付）

## 1. 问题与目标

工具型 Agent 除了调用模型，还需要组织工具执行、上下文、任务状态、运行限制和结果交付。使用者需要知道任务运行到了哪里、产生了什么成果、为什么失败，并能在后续版本中恢复任务和改进运行策略。

首批目标用户是需要委托小型代码修改的本地后端开发者。核心需求是：把真实仓库中的小修复交给 Agent，完成后检查代码 diff 和已有测试证据，再决定接收结果。项目也用于 Agent 岗位作品展示，但演示样例数量不作为产品优先级。自优化保留为后续研究方向，先以真实使用验证需求。

产品目标：

1. 能接收明确任务，在指定工作区自主调用工具并交付成果。
2. 执行过程可查看，失败有记录，运行受到明确限制。
3. 前端运行控制台与后端能力同步交付，后续同步扩展上下文管理、会话恢复和配置能力。
4. 能依据失败轨迹提出策略修改，经独立检查后采用或拒绝，并支持回滚。

技术栈、模型厂商及运行时复用方案记录于技术设计；本 PRD 约束产品能力，不要求复刻特定参考项目或从零重写全部组件。

## 2. 核心使用流程与交付物

基本流程：

提交任务和工作目录 → 加载运行配置 → 模型决策 → 执行工具 → 回传结果并继续 → 生成成果 → 执行预先配置的验收 → 展示结果与结束原因。

自优化流程：

选择失败记录 → 分析共性问题 → 生成受限候选修改 → 隔离试运行与回归检查 → 接受或拒绝 → 后续任务使用指定版本；需要时回滚。

每次任务至少交付：运行标识、执行状态、验收状态、结束原因、执行轨迹和产物位置。产物可以是生成文件、代码修改或结构化结果，不要求每个任务都修改代码。

## 3. 用户故事与完整功能范围

以下覆盖任务管理、模型接入、执行循环、工具、环境、上下文、会话、轨迹、配置扩展和自优化十类功能。

1. **任务管理（V0.1）**：作为使用者，我希望提交任务描述并指定工作目录，以便 Agent 在明确范围内工作；每次运行有独立标识。
2. **模型接入（V0.1）**：作为使用者，我希望配置一个支持工具调用的模型，以便完成多轮任务；模型请求超时或失败时能得到明确记录。
3. **基础工具（V0.1）**：作为使用者，我希望 Agent 能读取、搜索、创建或修改文件，以及执行命令，以便完成真实操作；工具输入经过校验，结果保留错误与退出状态。
4. **自主执行（V0.1）**：作为使用者，我希望 Agent 根据工具结果继续决策，直至完成、失败或触发限制，以便减少逐步手动指挥。
5. **运行控制（V0.1）**：作为使用者，我希望设置轮次、调用和超时上限，并主动中断任务，以便控制失控循环和长时间运行。
6. **轨迹和成果（V0.1）**：作为使用者，我希望查看消息、工具参数与结果、耗时、结束原因和生成文件，以便理解过程和定位问题；重启后仍能读取已保存记录。
7. **结果验收（V0.1）**：作为使用者，我希望系统执行我预先配置的验收程序，以便区分“模型结束回答”和“产物符合要求”。
8. **上下文管理（V0.2）**：作为使用者，我希望系统加载项目说明、控制工具输出、按需读取内容并压缩旧历史，以便处理更长任务；原始轨迹仍可追溯。
9. **会话恢复（V0.2）**：作为使用者，我希望查看历史任务并从可恢复检查点继续，以便保留进度；恢复前核对工具状态和工作区变化。
10. **前端运行控制台（V0.1）**：作为使用者，我希望通过任务列表与提交、任务详情和运行配置三个页面，提交任务、观察实时执行、取消运行并查看产物、验收与历史记录；这是必须交付的前端界面，详见 [前端需求](FRONTEND_REQUIREMENTS.md)。后续后端新增用户可见能力时同步提供对应前端操作或展示；优化记录页面与版本操作随 V0.3 交付。
11. **隔离执行（V0.2）**：作为使用者，我希望命令在独立容器工作区运行，以便限制文件与资源访问；任务取消和超时后能清理关联进程。
12. **配置扩展（V0.2）**：作为使用者，我希望保存任务预设、选择工具集合、加载技能，并替换声明的策略组件，以便适应不同任务；首版扩展不要求运行中热更新。
13. **失败诊断（V0.3）**：作为使用者，我希望系统从多条轨迹归纳重复调用、参数错误、上下文超限或缺少验证等问题，以便获得有证据的改进建议。
14. **候选生成（V0.3）**：作为使用者，我希望优化器只修改允许的提示词、工具说明和策略配置，以便控制变更范围；候选记录父版本、差异、来源轨迹和预期作用。
15. **版本晋级与回滚（V0.3）**：作为使用者，我希望查看候选试运行、回归结果和接受或拒绝理由，并切换或回滚版本，以便管理策略变化。
16. **经验复用（V0.3 进阶）**：作为使用者，我希望保存带适用条件和执行证据的有效经验，以便支持后续优化；保留失败和退化记录，避免只积累正面结论。

## 4. 版本边界

| 版本 | 必须交付 | 完成边界 |
| --- | --- | --- |
| V0.1：任务能跑完 | CLI、单模型接入、执行循环、四类基础工具、本地工作区、运行限制、持久轨迹、产物交付、简单验收，以及任务 API、SSE 和基础前端控制台 | CLI 与网页均能运行预置任务，留下成果、过程和明确状态；前后端联动验收通过 |
| V0.2：过程可管理 | 上下文策略、可恢复检查点、配置与技能、容器工作区，以及同步更新的前端操作与展示 | 能通过网页管理新增能力，并安全核对后恢复受支持的运行 |
| V0.3：策略能改进 | 失败归类、受限候选、隔离试运行、回归检查、版本晋级与回滚、优化记录页面 | 至少跑通一个真实修改的完整生命周期，包括拒绝或回退路径 |

V0.1 允许单进程、单任务串行运行和非流式模型请求；CLI 与前端均应显示真实执行阶段。插件生态、多模型路由、继续执行和自优化不属于 V0.1 完成条件。当前实施进度见 [项目概览](../PROJECT.md)，版本目标与实际交付分开维护。

### 4.1 前端控制台的交付范围

任务 API、SSE 事件订阅和前端运行控制台与后端功能同步开发和验收。基础控制台覆盖任务提交、实时详情、最终结果与产物、历史、运行配置和独立验收；后续上下文、恢复及优化能力同步提供对应操作。页面、状态和 F01—F08 标准见 [前端需求](FRONTEND_REQUIREMENTS.md)，基础入口不依赖容器或恢复执行。

### 4.2 前后端同步迭代与完成条件

每次后端修改都检查接口、数据结构、配置、工具能力、状态、事件和错误语义是否影响前端；有影响时，同一迭代同步更新前端调用、类型、页面、交互、相关测试和文档。确实不影响前端的内部变更，在交付说明中写明原因。

版本或功能迭代的 Plan 必须列出后端变更、对应前端功能、共享契约及联动验收方式。验收从页面实际提交或操作开始，核对后端执行、事件展示、最终状态与产物；仅后端测试通过不能代表用户可见功能已交付。未接入的能力明确显示不可用或未验证，不使用静态占位数据冒充已完成的联动。

## 5. V0.1 详细需求

### 5.1 输入与工具

输入包括任务描述、工作目录、运行配置，以及可选的验收入口。工作目录不存在、缺少必需配置或验收入口无效时，应在启动前给出可读错误。

基础工具覆盖：读取文件、搜索内容、创建或修改文件、执行命令。工具结果至少包含成功或失败、输出或错误；命令额外保留退出状态与超时信息。过长输出向模型返回有标记的截断内容，完整输出保存为可追溯记录；较大文件支持分段读取。

首版在用户指定的可信本地工作区运行。文件工具限制访问范围，命令设置工作目录、超时与清理逻辑。工作目录约束不等于命令沙箱；容器隔离在 V0.2 实现，V0.1 不承诺防护恶意任务。首版仅支持普通前台命令，进程树清理采用本地平台的最佳努力机制；后台守护或脱离父进程的程序暂不支持。清理无法确认时明确记录未知或不完整状态，不报告完整清理成功。

### 5.2 执行与终止

模型生成的工具名称和参数需校验，不能因为单次格式错误直接破坏运行。工具错误作为观察结果返回模型；宿主配置错误和不可恢复异常应终止并记录原因。

支持最大模型轮次、最大工具调用数、单次模型请求超时、单次命令超时和总运行时长限制。模型请求重试有上限；产生副作用的工具不得盲目自动重试。用户中断后停止调度新工具，并清理正在运行的关联进程。

费用与 token 先做统计；缺失的供应商用量标记为未知，不记为零。精确费用预算和多任务调度留到后续版本。

### 5.3 执行状态与验收状态

执行状态与验收状态分别展示：

| 执行状态 | 含义 |
| --- | --- |
| 已创建 / 运行中 | 任务已登记，或正在调用模型与工具 |
| 执行完成 | 模型结束本轮任务，尚不能单独证明结果正确 |
| 执行失败 | 遇到不可恢复的模型、工具或宿主异常 |
| 已取消 | 用户主动中断或上游任务取消，分别记录来源 |
| 已超时 / 达到上限 | 超过时长、轮次或调用次数限制 |

验收状态为“未验证、通过、未通过、验收异常”。没有验收入口时保持未验证；只有执行完成且验收通过，才展示为任务成功。验收失败不能覆盖原始执行记录。验收程序也需设置超时、输出上限和中断清理，总体时限涵盖验收阶段。断言不满足显示未通过，启动失败或超时显示验收异常；执行已完成时保留原执行状态，另行记录验收异常原因。具体验收协议在技术设计中确定。

验收入口由使用者预先指定，由宿主调用，不由模型自行选择评分标准。验收程序与工作产物分开管理；V0.1 的可信本地模式不作为强安全隔离。

### 5.4 记录与示例任务

运行记录应保存任务输入、配置快照、模型与工具消息、工具结果、时间、用量、结束原因、验收结果及产物位置。不得保存明文密钥。中断前已完成的关键步骤应落盘；不承诺任意时刻崩溃都无损。

固定日志样例用于验证通用执行与独立验收。CSV 和目录清单可以作为后续回归素材，但不再作为近期必须交付的产品功能。

### 5.5 真实项目任务与代码审阅

宿主登记已有 Git 仓库根目录、固定测试命令和所需 Python 源码搜索目录；页面选择项目、填写任务并指定提交基线。系统固定基线提交并创建独立工作树，不将源目录的未提交改动带入任务。项目命令在该工作树中执行，已有运行预算、轨迹、取消和独立验收机制继续复用。

终态后保存新增、修改、删除、重命名及二进制变更的证据。页面提供 diff、完整补丁下载、测试输出及审阅决定。保留只保留工作树和补丁，不自动提交或合并；丢弃须确认，仅移除已核验属于本任务的工作树，历史记录与补丁继续保留。审阅状态独立于执行和测试状态；测试通过不代表用户已接受修改。完整边界见 [代码任务与审阅](PROJECT_TASKS.md)。

## 6. V0.1 验收与测试决策

| 编号 | 验收场景 | 可观察的通过条件 |
| --- | --- | --- |
| A01 | 正常任务 | 真实模型至少完成一个可核对任务，产生实际修改或产物、完整轨迹与宿主验收证据 |
| A02 | 无效启动配置 | 未调用模型即返回清晰错误，不产生半启动任务 |
| A03 | 工具参数或执行错误 | 错误反馈给模型，后续可继续；不可恢复错误保留明确结束原因 |
| A04 | 命令或请求超时 | 能在配置边界附近停止对应操作，保留超时标记和相关输出 |
| A05 | 达到运行上限 | 不再调度新调用，保留已有产物和达到上限的原因 |
| A06 | 用户中断 | 停止后续调度；普通父子进程用例中关联进程被终止，已保存记录重启后可读；清理失败或无法确认时有明确状态 |
| A07 | 错误产物或无验收入口 | 分别显示验收未通过或未验证，不因模型声称完成而判成功 |
| A08 | 长输出与持久化 | 截断有提示、原始输出可追溯；历史记录能关联本次配置和产物 |
| A09 | 验收程序阻塞或失败 | 验收超时或启动失败后能结束并清理，显示验收异常；断言失败显示未通过，原执行状态保持不变 |

测试以外部行为和关键契约为准，重点覆盖执行终止、工具边界、记录持久化与验收结果。用固定模型响应验证稳定的工具循环和异常路径；用少量真实模型运行验证端到端接入。真实模型的每次必过不作为确定性工程测试条件。

前端与任务接口的验收遵循 [前端需求 F01—F08](FRONTEND_REQUIREMENTS.md)：每个切片覆盖受影响的页面与契约场景，基础控制台整体交付时完成全部联动验收。验收证据包括页面操作、实际接口请求、事件与持久化结果的一致性，不能以静态展示或仅后端测试通过代替。

离线确定性测试覆盖运行机制与异常路径；少量真实模型检查覆盖实际接入。历史测试结果与 F01—F08 页面证据集中在 [控制台验证记录](WEB_CONSOLE.md#7-已保留的验证证据)，最新交付范围见 [项目概览](../PROJECT.md)。真实项目额外验收源改动保留、基线固定、工作树测试导入、完整diff、保留/丢弃与重启读取；大规模数据集、统计显著性、多组对照和排行榜实验不属于 V0.1 验收。

## 7. 后续实现决策与自优化边界

技术设计需确定执行器、模型适配、工具执行、上下文、会话存储、运行服务和优化器等模块的职责；验收器与产物评分保持独立。

V0.2 恢复必须同时核对会话和工作区。对“工具可能已执行、结果尚未记录”的情况，先检查后置状态或标记待核对，不直接重放任意命令。网页事件订阅与任务生命周期解耦，客户端断开连接不等于取消任务。

V0.3 候选只可修改声明的提示词、工具说明和策略配置；验收器、隐藏测试、数据划分、权限、密钥与宿主预算不属于可修改对象。候选与正式版本隔离，记录来源、修改、运行结果和拒绝原因。初版先完成单条候选的提出、检查和接受或拒绝，再扩展候选搜索与经验库。

通过少量回归样例属于功能检查。宣称“能力提升”之前，还需独立的未见任务验证；开发阶段反复使用的验证结果不得当作最终泛化分数。

## 8. 暂缓事项与下一步

V0.1 暂缓：容器、会话续跑、复杂插件体系、多模型、MCP、长期记忆和自优化。任务 API、SSE 与基础前端属于 V0.1 必须交付范围。项目近期暂缓：桌面客户端、插件市场、多租户、分布式调度、训练模型权重、运行中任意自改内核，以及无验收入口的开放世界在线进化。

技术选型、模块接口、数据契约和实施顺序记录于 [技术设计](TECH_DESIGN_V0.1.md)，具体交付状态与下一步维护在 PROJECT.md。技术设计可以随实现证据调整，产品目标和版本边界以本 PRD 为准。

参考用于借鉴机制，不表示本项目已实现对应能力或复现论文结果。

- [Meta-Harness](https://github.com/stanford-iris-lab/meta-harness)：依据候选源码、轨迹和反馈改进 Harness。
- [RRSI](https://arxiv.org/abs/2609.24972)：限制进化过拟合、控制修改规模与复杂度。
- [Harness²](https://arxiv.org/abs/2610.14224)：面向新任务的递归 Harness 适应，作为后续研究参考。
