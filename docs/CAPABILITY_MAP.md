# Agent Harness 能力全景与建设顺序

- 盘点基线日期：2026-10-29；文档整理完成：2026-10-30。
- 定位：面向长期完整 Agent 工作台的产品能力盘点；当前首先服务本地开发者的代码任务。
- 基线：当前工作区源码、前后端接口与测试、已有验收记录，包含未提交改动；不等同于已提交或已发布版本。
- 最初盘点：只读核对实现与官方资料、整理文档；随后2026-10-30获批实现C03及相关C05/C12首版，工程与真实页面验收单列在[规划协议](PLANNING.md)，不与旧版验收混计。
- 文档关系：[PRD](PRD.md) 保留当前版本需求与验收基线；本文维护长期能力、大功能缺口及建议顺序；[PROJECT](../PROJECT.md) 提供项目导航。

## 1. 目前是什么，还缺哪几块

当前已经是一个**可以在本机项目里完成代码任务、连续对话、委派只读研究、观察过程、检查测试与差异的主 Agent 工作台**。基础执行、上下文管理和交付证据已经有较完整的实现。

主动规划、结构化任务与单机队列、项目长期记忆、只读并行与隔离开发、单机会话内团队已有首版。运行中补充、安全暂停接续及后台命令见[长任务协议](LONG_RUNNING.md)；2026-11-06接入[C16本机自动化](AUTOMATIONS.md)。长期缺口主要集中在：**任意执行中断的安全自愈、外部事件及云端自动化，以及记忆的后台整合和用户全局范围**。工具接入、模型接入、执行权限、结果采纳和评测也有后续空间。

这些功能不能仅靠增加几段提示词完成。例如，后台任务需要运行归属与恢复策略；Teams 需要任务认领、消息和代码归属；Plan Mode 需要宿主实际限制写入。下面按用户能完成的工作组织，而不是把接口、参数和按钮各算一项功能。

### 1.1 状态口径

| 状态 | 本文含义 |
| --- | --- |
| 已实现（当前范围） | 当前产品有对应后端、前端入口和已有验证依据；仅对明确写出的边界成立 |
| 部分实现 | 已有能使用的基础，但未形成该大功能的完整闭环 |
| 未实现 | 核对当前运行主线、数据模型、工具注册、API、前端及测试后，未发现该能力的产品闭环 |

优先级与状态分开：没有实现不代表必须立即开发。本文的长期范围和建议顺序已经纳入本次文档整理，但每轮功能开发仍需单独提交 Plan 并获批。

## 2. 先把容易混用的概念分开

### 2.1 用户目标、会话、运行和 Agent Task

| 概念 | 具体例子 | 当前映射与缺口 |
| --- | --- | --- |
| 用户目标 | “给这个项目增加登录功能” | 主要保存在用户消息中，尚无独立目标管理对象 |
| 会话 Conversation | 用户围绕登录功能连续讨论和修改 | 已有 `session_id` 和会话索引 |
| 单次运行 Run | 用户发一次消息，Agent 执行到结束 | 已有 `run_id`、状态、预算、事件、差异和验收 |
| 工作项 Agent Task | “设计接口”“实现后端”“实现前端”“联调验收” | 尚无独立工作项对象、依赖和负责人 |
| 工具调用 Tool Call | 读取文件或执行一次测试命令 | 已有调用标识与结果；不是一个完整业务工作项 |
| Agent 实例 | 负责后端实现的子 Agent 或团队成员 | 当前没有实例级生命周期、父子树或团队成员模型 |

本文将用户提到的 **agent task** 理解为可创建、更新、分派和跟踪的工作项，同时覆盖委派执行时与 Agent/Run 的关联。不同产品会用 `task` 表示待办项、异步作业或子 Agent 调用，后续设计必须明确区分，不能只照搬名字。

当前 `TaskSpec` 只是提示词、工作目录、Python 环境与验收配置；`parent_run_id` 表示同会话上一轮，不是父 Agent；`asyncio.Task` 是服务内部协程，不是用户能管理的 Agent Task。依据：[运行模型](../src/agent_harness/schemas.py)、[后台服务](../src/agent_harness/web/service.py)。

建议的长期关系是：一个用户目标对应一组工作项；工作项可跨多次 Run 完成；会话负责沟通；Agent 接受工作项并留下执行证据。是否把“用户目标”单独建模，可在 C04 首版设计时决定，不能把此建议当作已有数据结构。

### 2.2 六个核心术语的产品边界

| 功能 | 用户得到什么 | 不能用什么代替 |
| --- | --- | --- |
| Plan Mode | 先研究和审阅方案，批准后才能修改项目 | 在提示词里写“先计划”，但仍开放任意写入与命令 |
| Agent Tasks | 知道整体工作拆成哪些项，谁在做，被谁阻塞，完成依据是什么 | 会话列表、Run 列表或 Markdown 勾选框 |
| Subagents | 主 Agent 把明确子问题交给独立上下文的执行者，再汇总结果 | 同一个 Agent 换个角色提示词继续回答 |
| Agent Teams | 多个成员围绕共享目标持续分工、交换信息、协调任务与成果 | 同时启动几个无关联的 Run |
| Memory | 新会话仍能使用以前确认的项目事实、偏好和经验，并可纠正或删除 | 同会话摘要、原始日志长期保存、无限扩大上下文 |
| Background | 工作有独立生命周期，可以离开页面、查看状态、停止和处理故障 | 把协程命名为后台任务，或者仅把终端输出藏起来 |

上表是本项目的产品划分。参考产品的具体实现会变化，例如子 Agent 也可能支持消息；区分 Teams 的关键是共享任务与持续协作责任，而不是“是否能发消息”这一个开关。调研依据见第 7 节。

## 3. 已经具备的基础闭环

### C01 本地项目与自主代码执行

**场景：** 打开一个本机仓库，让 Agent 修复错误，查看实际改动和测试结果。

**当前交付：** 原生目录选择、最近项目、Git/普通目录识别；文件读取、搜索、整文件写入、带指纹校验的局部编辑和 argv 命令执行；CLI 与网页共用 Runner。默认在所选目录工作，显式 Git 隔离时一个会话复用一个工作树。Python 解释器、源码路径、命令与宿主测试保持当轮一致。

**边界：** 当前是可信本地、单任务、单 Agent。不能将工作树描述成命令沙箱；普通文件夹与 Git 项目的测试设置能力也有差异。复杂能力的缺口归入 C06、C10—C14，不把每个工具参数作为新一轮大功能。

**前后端证据：** [项目登记](../src/agent_harness/web/project_catalog.py)、[工具执行器](../src/agent_harness/tools/registry.py)、[Runner](../src/agent_harness/runtime/runner.py)、[项目页](../frontend/src/pages/ProjectPage.tsx)、[项目入口回归](../tests/web/test_project_catalog.py)、[文件工具回归](../tests/tools/test_file_tools.py)。实际联动记录见 [可靠性复验](RELIABILITY_ACCEPTANCE_20261029.md)。

### C02 多轮会话与上下文管理

**场景：** 第一次修改后补充要求；会话变长后继续工作；程序中断后先核对现场，再发“继续”。

**当前交付：** 线性会话、逐轮结果与差异、幂等发送；继承已核验历史与当前代码；固定根 AGENTS.md 和所选技能；输入字节预算、输出外置、旧成功结果遮蔽、结构化摘要与 `read_context` 回读。

**边界：** 重启后读取历史不会自动续跑。“继续”创建新 Run，不是从某一代码行恢复；未知工具结果不能自动重放。当前根项目指令加载不包含完整的分层规则发现。运行中不能提交新一轮；会话分叉及代码分叉没有产品闭环，应随 C05/C13 的场景设计。跨会话知识归 C09。

**前后端证据：** [会话重建](../src/agent_harness/storage/sessions.py)、[压缩](../src/agent_harness/context/compression.py)、[上下文归档](../src/agent_harness/context/archive.py)、[会话发送](../frontend/src/hooks/useConversationSend.ts)、[上下文面板](../frontend/src/components/ContextPanel.tsx)、[中断接续测试](../tests/web/test_interrupted_continue.py)、[压缩 API 测试](../tests/web/test_compression_api.py)。

## 4. 核心缺口：任务如何被组织和执行

本节的“应补齐”“前端”“完成标准”是建议的产品范围，不是本轮已经开发的能力，也不是未经批准的新版本承诺。

### C03 Plan Mode：先形成方案，再批准执行

- **具体场景：** 用户要求重构认证模块，先查看方案与改动范围；调整方案后批准，再开始修改代码。
- **当前状态：已实现首版，最终验收见[规划协议](PLANNING.md)。** 自动入口下Agent可主动调用进入规划、提问、提交方案和更新进度；用户也可手动选择先规划。宿主`planning_policy=required`从运行开始强制只读，避免依赖模型是否及时切换。
- **当前交付：** 版本化方案包含目标架构、范围、步骤及验收，用户可批准/修改/拒绝；批准绑定当前请求、方案版本和实际目录对象。规划写入、局部编辑、所有命令与宿主测试均被拒绝/跳过；目录发现使用只读工具。状态保存在受保护运行记录。
- **前端闭环：** 原会话回答问题、审阅并决定方案；批准后自动接续，显示对应计划和步骤；历史只读、各版方案与用户决定可回看。等待状态不冒充开发完成。
- **边界：** 自动模式的复杂度判断仍由模型完成，严格先批准需显式入口或宿主策略；批准范围依靠方案约定与既有工具/路径/预算限制，不声称形式化理解自然语言范围。CLI可保存等待，但交互式决定首版限网页登记会话。
- **验收与依据：** 复用C02幂等追加和当前单槽，等待结束当前Run、回答后建立新Run，重启只读不重放；不是持久协程精确恢复。[规划实现](../src/agent_harness/work/planning.py)、[工具注册](../src/agent_harness/tools/registry.py)、[页面](../frontend/src/components/PlanningPanel.tsx)、[真实API测试](../tests/web/test_planning_api.py)；对应PRD PM01—PM09。

### C04 Agent Tasks：可追踪的整体工作与子任务

- **具体场景：** “增加登录功能”被拆成接口设计、后端、前端和联调；用户能看到哪些完成、哪些被依赖阻塞，失败后接着处理剩余项。
- **当前状态：首版已实现。** 独立工作项、四个模型工具、父子/依赖、版本核验、宿主认领、证据和跨轮接续共用持久服务；前端可管理，计划进度统一投影。仍是单 Agent，跨会话共享和多人认领待后续。详见[任务协议](TASKS.md)。
- **应补齐：** 持久工作项、目标及完成条件；待处理、执行中、阻塞、完成等业务状态；父子关系与依赖；创建/更新/查询工具；与 Run、成果和验收证据关联。单 Agent 也应能使用；进入多人 Agent 协作后再增加原子认领、释放和转派规则。
- **前端闭环：** 会话或目标下有简洁任务列表，看到当前项、阻塞原因和证据；可修改范围或取消任务；从任务进入对应运行。模型声称完成和检查通过分别显示。
- **完成标准：** 依赖未满足时不误标可执行；重复请求不创建两份任务；刷新、续轮后任务状态保持；任务完成可追到产物或验证；失败保留已完成项并能明确接续剩余工作。
- **依赖与依据：** C03 可以产出任务，但不要求所有小任务先写计划；C04 是 C08 的共享任务基础。当前 [运行模型](../src/agent_harness/schemas.py) 和 [会话索引](../src/agent_harness/web/conversation_index.py) 不应被改名冒充任务系统。参考 [Deep Agents 的任务规划](https://docs.langchain.com/oss/python/deepagents/overview#task-planning)。

### C05 运行中人机协作：提问、批准、纠偏与接管

- **具体场景：** Agent 不确定业务规则时暂停提问；用户运行中补充“先别改数据库”；需要批准某项操作时保留现场等待答复。
- **当前状态：本机首版已实现。** 提问、方案及具体动作审批继续沿用[权限协议](PERMISSIONS.md)。本轮新增本轮补充、下一轮排队、安全边界跳过旧参数、处理确认、协作式暂停、父子收拢及剩余预算接续，详见[长任务协议](LONG_RUNNING.md)。暂停不声称冻结进程或自动恢复未知副作用。
- **应补齐：** 会话分支与代码分支联动，以及按实际需求进一步接管；任意进程内存现场恢复不在当前范围。
- **前端闭环：** 显示“正在执行 / 等待你回答 / 待批准 / 暂停”等真实状态；用户能回答、拒绝、补充约束或停止；消息已接收与已被 Agent 处理要能区分，刷新不丢待处理问题。
- **完成标准：** Agent 等待时不继续执行依赖该答案的动作；答复只消费一次；旧审批不能批准新参数；取消等待后不会因迟到答复恢复；运行中纠偏应用于后续动作并留下记录。
- **依赖与依据：** 与 C03/C12 共用既有计划和权限，暂停及恢复复用 C06 队列；[控制器](../src/agent_harness/runtime/control.py)、[发送入口](../frontend/src/hooks/useRuntimeControl.ts)与[长任务回归](../tests/runtime/test_long_running.py)共同约束实际行为。

### C06 后台执行与持久任务调度

- **具体场景：** 一个项目执行长任务时，在独立项目继续工作；页面离开后仍可定位、停止和处理决定，重启后知道哪些可以调度、哪些必须核对。
- **当前状态：本机跨项目首版已实现。** 默认双槽，原持久队列统一管理准备、执行及证据收尾；同会话、同仓库、重叠目录和显式共享资源组串行。全局模型和进程限流覆盖父子执行、Hook 及验收。协议与验收见[调度与恢复](SCHEDULING.md)。
- **恢复：** 用户可明确开启未开始请求的启动恢复；已有可信终态自动对账，未知动作及清理结果局部阻塞，不重放。桌面彻底退出仍安全收尾，不承诺原进程现场恢复。
- **前端闭环：** 分组显示需要处理、运行、排队与结束，展示容量和真实等待原因；可定位占用作业、单项停止及保存启动恢复选择。桌面/Web/CLI 共享后端资源规则。
- **完成标准：** 并发不越限，跨项目状态与权限不串线；同仓库及目录冲突受控；取消覆盖所属后代；重启不将孤儿运行视为正常活动，未知外部副作用不自动重放。
- **后续缺口：** 任意中断步骤安全自愈、同仓库多个主会话并行及进一步通知；分布式仍按需求规划。C16本机首版已在同一链路增加触发与精确授权，见[自动化](AUTOMATIONS.md)。

### C07 Subagents：主 Agent 委派独立子工作

- **具体场景：** 主 Agent 实现接口，同时让只读子 Agent 检查已有调用方，收到带文件依据的报告后统一修改和验证。
- **当前状态：只读并行、隔离开发及成果交接已实现。** 探索/审阅拥有独立角色提示与显式技能，宿主限制父权限交集；返回后暂停同批后续工具，父读取结果后重新决定。原总预算内保留父收尾额度，末轮禁工具总结；统一结构报告核验实际证据引用，区分必要修复、可选建议和部分完成。网页及历史同步展示限制、未完成事项、来源、上下文与轨迹。完整协议、官方参考及验收见[只读子 Agent](SUBAGENTS.md)。已支持最多两个活动子项、异步启动/查询/等待和单项取消，父停止收拢全部，未消费预算不可重复分配；开发委派、审批专用接续、固定成果和父工作区集成见[开发协议](DEVELOPMENT_SUBAGENTS.md)；任意resume保留后续。
- **应补齐：** 子 Agent 的职责与输入、独立上下文、可用工具/模型/权限配置；创建和结果回收；失败/超时/取消传播；总预算分配；只读共享目录与写入隔离策略。主 Agent 必须知道哪些结果已完成、哪些仍在执行，不能把启动成功视为任务完成。
- **前端闭环：** 在会话活动中查看委派任务、执行者、状态和结果摘要；展开查看子执行记录、用量、改动及失败；停止主任务时说明子工作如何处理。
- **完成标准：** 主 Agent 能使用子结果交付一个真实任务；子历史不会无条件灌入主上下文；子权限不能超出父级授权；多个子任务共享总预算；子失败不会伪造成功；取消后无未归属进程或写入。
- **当前交付：** 只读委派之后已建设隔离开发与成果集成，首版沿用可信本机权限，固定父实际代码，用户确认采纳；互不重叠成果可组合候选统一检查，同路径重叠明确阻止自动组合。任意递归、成员通信与Teams继续保留后续。
- **依赖与依据：** 最小串行委派可复用现有 Runner；并行委派需要 C06，可靠写入需要 C12/C13，任务关联使用 C04。核对 [执行循环](../src/agent_harness/runtime/agent.py)、[工具注册](../src/agent_harness/tools/registry.py)、[前端类型](../frontend/src/types.ts)。参考 [Claude Code 子 Agent](https://code.claude.com/docs/en/sub-agents)。

### C08 Agent Teams：多成员共享目标并持续协作

- **具体场景：** 一个成员负责后端、一个负责前端、一个负责验收；接口约定变化时相互通知，任务有依赖，最后整合到可运行的成果。
- **当前状态：单机会话内首版已实现。** 已有稳定团队/成员、原C04任务原子认领、持久消息、C07共享预算和双槽、未采纳依赖成果、C13整体采纳、停止及重启待核对。协议和验收边界见 [团队协作](TEAMS.md)；真实样例包含审批及失败后人工继续，不代表普遍无人值守可靠性。
- **本轮范围：** 已补齐团队/成员生命周期、原任务认领、消息、双槽调度、工作区归属、依赖成果、整体采纳和停止核对；成员空闲、失败或停止都有明确状态。失联后不重放未知操作，需核对后明确接管。分布式、多供应商与无人值守可靠性属于后续范围。
- **前端闭环：** 一个团队视图看成员、任务与阻塞关系；可查看某个成员会话、发送指示、调整任务；总览展示集成状态和总用量。多个成员的“完成”不能直接合成团队“完成”。
- **完成标准：** 一个跨前后端任务确实由多个成员协作完成并通过集成验收；依赖约束生效，认领不重复；成员退出后工作可重新归属；并行修改冲突显式暴露；解散团队后运行和工作树可核对，历史仍保留。
- **依赖与依据：** 依赖 C04、C06、C07 以及 C12/C13 的写入与集成边界；C15 需要聚合观测。参考 [Claude Code Agent Teams](https://code.claude.com/docs/en/agent-teams)，该官方页面在调研时仍标注实验功能。本文不以对方功能名称或“人数多”作为收益证据。

### C09 Memory：跨会话保留可维护的知识

- **具体场景：** 用户在新会话要求继续开发时，Agent 已知道项目测试约定、已确认的架构决策和用户偏好；事实过期后可纠正，而不是反复引用旧结论。
- **当前状态：部分实现。** 已有根项目指令快照、同会话历史与摘要。本轮已实现项目级持久记忆、人工保存、Agent 候选、跨会话文本检索、来源版本与维护界面，验收见[项目记忆](MEMORY.md)。用户全局记忆和后台整合仍待后续。

| 记忆层 | 例子 | 当前判断 |
| --- | --- | --- |
| 项目固定指令 | “新增函数必须有中文职责说明” | 根 AGENTS.md 加载已实现；分层规则与专门管理仍不足 |
| 当前会话工作记忆 | 做过什么、工具输出在哪里、下一步是什么 | 已有历史、摘要和回读 |
| 项目长期知识 | 已确认的架构决策、反馈、信息入口和适用条件 | 本轮实现项目级维护、跨会话检索和来源版本闭环 |
| 用户长期偏好 | 回答语言、交付习惯 | 尚无产品级用户记忆范围与管理 |
| 执行经验 | 某类失败的可靠处理方式及适用条件 | 已实现带实际结果和适用边界的项目经验，真实收益按独立样例验收 |

- **应补齐：** 明确项目/用户作用域；记忆内容、来源、适用条件、更新时间；显式“记住”及可选自动候选提取；检索和注入预算；冲突、过期和错误记忆处理；查看、修改、删除。长期记忆不能无条件提升成宿主权限或替代当前用户指令。
- **前端闭环：** 项目中能查看和管理记忆，运行详情能说明本轮用了哪些记忆；用户可以拒绝保存或纠正一条事实。优先展示有用内容和来源，不用给每个向量参数做设置页。
- **完成标准：** 在会话 A 保存确认的项目事实，会话 B 能按需使用；另一项目不会串入；修改/删除后新运行生效而旧轮快照可追溯；矛盾事实不会静默覆盖；压缩上下文不会丢失应保留的来源关系。
- **依赖与依据：** 复用 C02 的输入投影和快照，可独立于 Teams 开发；首版可以使用 Markdown/结构化记录与文本检索，不预设向量数据库。[上下文构造](../src/agent_harness/context/builder.py)、[会话历史](../src/agent_harness/storage/sessions.py)、[上下文面板](../frontend/src/components/ContextPanel.tsx)。参考 [Claude Code memory](https://code.claude.com/docs/en/memory) 与 [LangGraph 的线程状态和跨线程存储区分](https://docs.langchain.com/oss/python/langgraph/persistence)。

## 5. 支撑完整工作台的其他大功能

### C10 Skills、MCP 与工具扩展

- **具体场景：** 为审阅任务选择专用流程，按需读取技能模板；连接一个代码托管或知识库服务，用统一工具完成查询或操作。
- **部分实现。** 页面可管理导入副本及宿主登记技能，支持手选和按需自动启用，受控读取文本资料并保存实际用过的版本。MCP 支持 stdio 和 Streamable HTTP、连接审核、工具发现、逐轮选择、参数审批与历史。 [任务技能](SKILLS.md) · [MCP 协议](MCP.md)
- **Hooks 已接入：** 宿主/项目统一规则、定义与入口脚本审核、串行生命周期处理、具体命令审批、阶段检查点、后台命令真实结束、父子与压缩事件、有限 Stop 续跑，以及桌面/Web 设置和历史记录；边界与验收见 [Hooks 协议](HOOKS.md)。核心权限、预算、记忆规则及独立验收继续由宿主强制执行。
- **待扩展范围**包括技能脚本的专用执行入口、扩展分发、MCP OAuth 登录及资源和提示模板浏览。HTTP、MCP 和模型判定型 Hook 按需规划。
- **前端闭环：** 管理可用技能与外部连接，区分断连/未授权/可用；运行中展示实际调用的外部工具及结果来源；授权只赋予明确范围。
- **完成标准：** 从页面连接并调用一个真实或可控 MCP 服务，重连、撤权、超时行为一致；技能资源按选择加载并留下快照；外部工具不会绕过 C12 权限，密钥不进入日志；刷新历史仍能说明当时的扩展版本和使用结果。
- **依据：** [技能实现](../src/agent_harness/context/skills.py)、[技能选择器](../frontend/src/components/SkillSelector.tsx)、[技能 API 测试](../tests/web/test_skills_api.py)、[技能说明](SKILLS.md)。参考 [MCP 架构](https://modelcontextprotocol.io/docs/learn/architecture) 和 [Hooks 生命周期](https://code.claude.com/docs/en/hooks)。

### C11 模型接入与按角色配置

- **具体场景：** 用户选择不同供应商；简单探索和复杂实现使用适合的模型；模型生成过程中能逐步阅读回答。
- **当前状态：已实现用户登记端点及多模型。** Chat Completions 连接共用工具、错误、用量与流式契约。Web 和 CLI 从宿主配置读取自定义地址与环境变量，桌面按端点版本加密保存。新会话显式选择模型，探索和审阅可覆盖。已接纳运行、审批接续与自动化按冻结端点校验执行。
- **前端闭环：** 设置页管理供应商和角色，新会话选择模型，运行诊断和委派详情展示实际供应商、模型、用量和错误。
- **验收范围：** 两个独立登记的连接通过跨服务委派与审批接续验证。缺密钥、限流、断流和历史均通过离线验证。
- **后续：** 更多供应商、能力目录、命名预设、路由或故障切换按使用需求另行规划。
- **依据：** [模型供应商与角色配置](MODELS.md)、[模型协议](../src/agent_harness/providers/base.py)、[联动测试](../tests/web/test_model_providers.py)。

### C12 执行环境与权限控制

- **具体场景：** 用户让 Agent 研究项目时允许读取；批准开发后允许指定目录写入；运行不熟悉的代码时使用隔离环境，并限制网络与资源。
- **当前状态：部分实现。** 宿主上限、三种会话模式、文件目录范围、规划只读和子 Agent 只读继承已统一。文件写入/编辑、模型命令及宿主验收均有执行前判定和持久动作审批；默认本机命令及验收需逐项批准，旧参数或旧权限不能批准新动作。命令仍在本机执行，尚无操作系统进程/网络沙箱或容器后端。Git工作树只隔离代码目录；具体契约与验收见[权限控制](PERMISSIONS.md)。
- **应补齐：** 进程和网络隔离、扩展工具授权、可选隔离执行环境、依赖准备及资源限制。当前审批不能约束获批命令的全部文件和网络访问；执行环境与代码工作区分别建模，不能把“隔离工作树”按钮当作两者都已隔离。
- **前端闭环：** 明确展示工作目录、执行环境和权限范围；需要批准时展示将执行的具体动作；环境不可用时解释失败，不能静默切回本机。
- **完成标准：** Plan Mode 的写操作被宿主拦截；子 Agent 不可扩大权限；命令与项目测试使用同一目标代码和执行环境；取消/超时后可核验清理；越界访问和网络策略按承诺生效。
- **依据：** [工作区约束](../src/agent_harness/execution/workspace.py)、[执行环境](../src/agent_harness/execution/python.py)、[进程管理](../src/agent_harness/execution/processes.py)、[工作树管理](../src/agent_harness/projects/manager.py)、[项目审阅面板](../frontend/src/components/ProjectReviewPanel.tsx)。首版具体隔离环境需另行选择，不预设必须支持所有平台。

### C13 成果审阅与采纳交付

- **具体场景：** 用户审阅 Agent 在隔离工作树完成的修改，采纳到指定分支；有冲突时解决后重新测试，再决定提交或创建 PR。
- **当前状态：部分实现，C13本机采纳首版已交付。** 固定成果、同仓库已登记目标、独立三方合并、冲突解决、候选检查、确认写回、原索引保护、实际目标复验、多轮/多目标增量、逐文件对账和受保护撤销已贯通桌面/Web。保留工作树的原有含义不变，不自动提交或推送，见[成果采纳](INTEGRATIONS.md)。
- **应补齐：** 经用户明确授权的提交/PR交付、更多版本控制形态及多Agent写入后的集成策略；首版目标使用当前已检出工作区，不自动切换分支。完整C13仍保持部分实现，C12操作系统隔离不计作已完成。
- **前端闭环：** 清楚区分“生成成果”“审阅通过”“已采纳”“已提交/创建 PR”；展示操作目标、冲突和最新测试依据；提供可审阅的最终变更。
- **完成标准：** 指定目标收到正确改动，原有未提交修改不被覆盖；冲突和测试失败时不伪造交付成功；重复操作不重复采纳；历史补丁和产物仍可下载；提交与推送遵守明确授权范围。
- **依据：** [项目管理](../src/agent_harness/projects/manager.py)、[本地文件证据](../src/agent_harness/execution/local.py)、[文件差异](../frontend/src/components/FileChangesPanel.tsx)、[审阅交互](../frontend/src/components/ProjectReviewPanel.tsx)、[产物 API 测试](../tests/web/test_artifact_collection_api.py)。

### C14 验证、评测与持续改进

- **具体场景：** 判断某个新策略是否减少人工接续，或者多 Agent 是否真的提高交付质量，而不是只增加输出与调用次数。
- **当前状态：部分实现。** 已有宿主项目测试、独立检查、有限自动修复与真实任务验收。V0.3 的一项受限候选比较、采用/拒绝及回退尚未闭合。自动修复只在公开项目测试失败后尝试修代码，不是自动优化 Harness。
- **应补齐：** 固定任务、起始代码、模型、环境与预算的比较流程；任务集与运行证据关联；比较质量、干预次数、耗时及已知成本；候选采用/拒绝、回退和未见任务回归。评测页面可以随重复使用需要演进，首轮无需先造平台。
- **前端闭环：** 首版可用现有运行详情查看基线/候选与各自检查；后续提供成对比较和回归结果，保留失败与人工介入记录。
- **完成标准：** 同条件跑完一组比较并可复查；候选不得继承基线已修改代码或修改独立检查；无收益能明确拒绝；采用后有可验证回退路径。样本规模不足时不宣称普遍性能提升。
- **依据：** [验收器](../src/agent_harness/runtime/verifier.py)、[自动修复测试](../tests/runtime/test_auto_repair.py)、[验收面板](../frontend/src/components/VerificationPanel.tsx)、[可靠性报告](RELIABILITY_ACCEPTANCE_20261029.md)、[PRD 的 I01—I05](PRD.md#46-受限改进首版v03)。

### C15 运行观察与资源管理

- **具体场景：** 用户判断任务卡在模型、命令、等待回答还是子 Agent；检查整个目标消耗了多少资源，并能停止所有相关工作。
- **当前状态：部分实现。** JSONL 事件、配置快照、完整已捕获输出、SSE、结束原因、已知 token、耗时和三项任务预算已经存在；已有父子/团队共享预算及跨 Run 容量、状态和阻塞总览；费用估算及费用预算仍未提供。
- **应补齐：** 任务—Run—Agent—工具的关联追踪；队列、等待与执行耗时；子预算分配及整体停止；按供应商可知数据估算费用、缺失和估算标识；多运行故障定位及必要通知。运营指标应服务实际判断，不先做大量仪表盘。
- **前端闭环：** 从总目标逐级进入失败环节，看到谁在运行、在等什么以及总预算；可定位原始日志和输入配置，历史与实时状态口径一致。
- **完成标准：** 父子用量不重复计数，未知数据不记零；超过总预算停止新增工作并收尾；断线重连不重复展示事件；可以从一条失败追到相应 Agent、工具和输出。
- **依据：** [记录存储](../src/agent_harness/storage/runs.py)、[运行检查器](../frontend/src/components/RunInspector.tsx)、[事件轨迹](../frontend/src/components/EventTrail.tsx)、[用量展示](../frontend/src/components/UsageDisplay.tsx)、[SSE Hook 回归](../frontend/src/hooks/useRunEvents.test.tsx)。

### C16 定时与事件驱动自动化

- **具体场景：** 每天检查项目测试；收到某个仓库事件后分析问题；长任务完成或需要用户批准时通知。
- **当前状态：本机首版已接入。** 时间/普通主运行事件规则、版本及内容绑定的持续授权、幂等接纳、重叠/漏跑、启停、收件箱及桌面通知复用原队列与Runner，见[协议与验收](AUTOMATIONS.md)。
- **后续缺口：** 外部Webhook与代码托管事件、云端托管、关机执行。当前按本机宿主在线执行，不重放未知副作用；操作系统沙箱仍属C12独立范围。
- **前端闭环：** 新建和修改规则、查看下一次执行、暂停、查看触发历史与结果；只在完成、失败、实质变化或需要处理时通知。
- **完成标准：** 重启后规则仍在；同一触发不会重复产生副作用；时区正确；长任务重叠按规则处理；撤销授权或暂停后不再启动；无交互环境遇到待批准动作能等待或明确终止。
- **依赖与依据：** 需要 C06 持久调度、C05/C12 的无人值守处理及 C15 通知；重用 [任务 API](../src/agent_harness/web/api.py) 与 [Runner](../src/agent_harness/runtime/runner.py)。可复用外部调度基础设施，但需要本产品的完整管理与记录闭环。

### C17 联网研究与多模态工作

- **具体场景：** 为依赖升级查官方文档；读取设计截图；分析 PDF/表格；启动页面并检查真实界面。
- **部分实现。** 受控 MCP 已支持官方文档和公开网页搜索、正文读取、来源链接和逐轮历史证据。 [通用网页搜索与原文读取](MCP.md#通用网页搜索与原文读取)
- **待补能力**包括附件输入与解析、图像等模型能力、浏览器会话和页面证据。可通过 C10 接入成熟工具。外部页面与文档内容始终作为待分析数据处理。
- **前端闭环：** 添加附件或 URL，展示加载/解析状态、引用来源与截图或产物预览；失败时说明哪些内容未读到。
- **完成标准：** 完成一个实际工作流，例如查官方文档→修改代码→浏览器验证→交付截图和差异；文件大小、解析失败、页面访问和模型能力不匹配均有明确结果。
- **依据与优先级：** [当前工具注册](../src/agent_harness/tools/registry.py)、[模型协议](../src/agent_harness/providers/base.py)、[消息输入](../frontend/src/components/ConversationPanel.tsx)、[产物面板](../frontend/src/components/ArtifactPanel.tsx)。联网研究较贴近代码任务；复杂多模态按需求选择，不自动作为核心版本门槛。

### C18 工作台接入与多人部署

- **具体场景：** 从另一台设备访问工作台，或多名用户各自运行项目任务；也可能希望在 IDE 内使用同一套运行服务。
- **当前状态：部分实现。** Windows Electron 桌面为主要入口，另有本机 Web 控制台与 CLI，共用 Python 执行核心；原生目录、加密凭据、文件操作、后台生命周期及打包见[桌面说明](DESKTOP.md)。仍面向可信本地单用户，移动布局不意味着具备安全远程服务或多人协作。
- **应补齐：** 若扩展远程/多用户，则需要认证、用户/项目授权、记录与凭据隔离、并发配额、执行环境隔离和审计；IDE 接入按实际需求评估。这里的“多人”指人类用户，不是 C08 的多 Agent。
- **前端闭环：** 根据部署目标提供身份与项目范围、权限反馈、用户隔离的会话和产物；IDE/桌面展示复用同一后端事实。
- **完成标准：** 用户无法读取或操作其他用户的任务/凭据/文件；不同入口的取消和结果一致；多人执行受配额和隔离策略约束。仅修改监听地址不算完成。
- **依据与优先级：** [Web 入口](../src/agent_harness/web/api.py)、[宿主配置](../src/agent_harness/web/config.py)、[CLI](../src/agent_harness/cli.py)、[前端入口](../frontend/src/App.tsx)。目前没有明确多人目标，列入长期选择，不建议抢在核心任务能力之前建设。

## 6. 建议的建设顺序

### 6.1 当前版本与长期路线如何并存

V0.2 的既定首版验收已经完成，仍允许人工接续。这个事实与长期缺少 Plan Mode、Memory、Subagents 等能力并不冲突。现有 V0.3 是“一项有证据的受限改进”，不应借此次盘点改称完整 Agent 工作台已经完成，也不应把全部长期能力追溯加入 V0.2 的欠账。

建议保留 C14 中现有 V0.3 的独立比较与决策工作，作为交付质量主线；新增大功能按下表组织。下表是**实施顺序建议，不是已批准的开发计划或固定版本号**。每一轮都应交付能从页面使用到结果核对的完整闭环，阈值调优和小修补并入相应功能。

### 6.2 核心工作台主线

| 建议顺序 | 一轮完整的建设主题 | 主要能力 | 为什么放在这里 | 该轮交付的实际效果 |
| --- | --- | --- | --- | --- |
| 1 | 可批准的规划与执行流程 | C03 + C05 的提问/审批 + C12 的宿主权限基础 | 先让用户控制工作范围，也为后续委派提供可执行授权边界 | 选规划→研究→回答问题→审阅并批准→执行→核对结果；未经批准不能修改项目 |
| 2 | 有任务清单的后台工作中心 | C04 + C06，配套 C15 状态观察 | 先让工作有稳定身份、依赖和运行归属，再增加多个执行者 | 拆任务→排队执行→后台查看/停止→失败或重启后核对接续；任务与 Run 可以相互定位 |
| 3 | 项目长期记忆 | C09，配套 C02 输入与快照 | 减少每次重新解释项目，且不必等待多 Agent | 保存确认事实→新会话按需使用→查看来源→纠正/删除→新运行生效 |
| 4 | 主 Agent 与专业子 Agent 协作 | C07 + C15 聚合预算/观测 | 有任务、权限和调度后，委派结果才可控可查 | 主 Agent 委派只读探索/审阅→回收结果→完成真实代码任务→统一验收 |
| 5 | 可审阅的动作授权 | C12 + C05 | 在隔离与写入委派前明确宿主、会话和子权限，防止只依赖模型文字约定 | 查看实际权限→审批具体动作→宿主执行原参数→查看结果与历史；协议见[Permission](PERMISSIONS.md) |
| 6 | 可隔离、可采纳的代码交付 | C12 的执行隔离 + C13，扩展 C07 写入委派 | 多个写入者必须有代码归属、成果集成和复验 | 子工作区执行→审阅差异→处理冲突→采纳到目标代码→复验；按授权交付提交/PR |
| 7 | Agent Teams 协作开发 | C08，复用 C04/C06/C07/C13/C15 | 共享任务和成果集成具备后，再增加成员间协调 | 多成员分工、沟通接口、认领依赖任务，交付通过集成检查的前后端功能 |
| 8 | 定时与事件驱动的持续工作 | C16，复用 C05/C06/C12/C15 | 无人值守需要可靠归属、授权、故障处理和通知 | 规则触发→去重调度→执行→记录结果→必要时通知，重启和重叠行为明确 |

“顺序 2”涉及面较大，正式 Plan 可按完整场景分成两轮：先交付任务清单与单机排队后台中心，再交付后台命令及服务故障恢复。每轮都必须说清实际支持的故障边界，不把仅加队列表或后台按钮视为完成 C06。

长期记忆可以提前或与后台中心交错推进；串行只读子 Agent 也不必等完整持久调度完成。上表优先保证产品依赖清楚，不把所有建议都包装成不可变的技术依赖。

### 6.3 按需求插入的能力主线

| 主题 | 何时值得插入 | 不能遗漏的关联工作 |
| --- | --- | --- |
| C10 工具与技能扩展 | 现有任务反复需要外部资料、代码托管操作或专用流程时 | C12 权限、凭据管理，C15 调用观察；先接一条真正有用的完整链路 |
| C11 多模型与流式交互 | 当前模型覆盖不足、用户明确需要其他供应商或角色模型时 | 统一工具/错误/用量语义及前端；不为 Subagents 强制先引入多供应商 |
| C14 评测与改进 | 现在就有失败证据；每项大能力上线后都应比较收益和退化 | 保留原始失败、人工干预和统一条件；作为持续质量主线 |
| C17 联网与多模态 | 联网研究、界面验证、文档任务成为真实使用需求时 | 可经 C10 复用工具，同时处理附件、来源、外部内容和模型能力 |
| C18 远程/多人/IDE 接入 | 目标用户和使用地点明确变化时 | 远程/多人必须先满足身份与隔离；本地 IDE 接入无需绑上云平台 |

### 6.4 一条完整场景检查这些功能是否连得起来

以“给现有项目增加登录功能”为例，长期完整流程应当是：

1. 用户进入 Plan Mode，Agent 读取项目和已确认记忆，提出接口、数据与验证方案；缺少业务规则时提问。
2. 用户批准具体版本，方案转成可跟踪的工作项，记录依赖与完成标准。
3. 主 Agent 委派独立探索或审阅；需要持续前后端协作时才组建 Teams。
4. 后台中心调度工作；成员只能在授权环境和所属代码范围内执行，用户可以查看进度、补充要求或停止。
5. 成员交换接口变更，处理阻塞；结果进入统一集成与检查，不直接把成员的自评当验收。
6. 用户审阅集成 diff，采纳到目标分支并复验；需要时明确授权提交或 PR。
7. 保存有来源的项目事实与可复用经验；后续新会话按需读取，评测记录说明哪些结果需要人工介入。

当前能覆盖其中的本地执行、会话续轮、基础上下文、测试、diff 和产物部分。其他步骤在前文明确标为缺口；这条流程用于检查未来架构是否连通，不是当前演示能力。

| [Deep Agents 概览](https://docs.langchain.com/oss/python/deepagents/overview) | Harness 覆盖上下文、文件、子 Agent、记忆与人机交互；结构化任务跟踪是可选择的能力 | 任务清单与子 Agent 是两项不同能力；应按场景引入，不必无条件增加复杂度 |
| [LangGraph Persistence](https://docs.langchain.com/oss/python/langgraph/persistence) | 区分单线程状态检查点与跨线程存储 | 当前会话历史不能直接宣称覆盖跨会话长期记忆 |
| [LangGraph Checkpointers](https://docs.langchain.com/oss/python/langgraph/checkpointers) 与 [Interrupt](https://reference.langchain.com/python/langgraph/types/interrupt) | 检查点支持恢复；等待输入可持久化，恢复可能重新进入节点 | 恢复设计必须处理副作用、去重和不确定结果；保存日志不足以承诺精确续跑 |
| [MCP 架构](https://modelcontextprotocol.io/docs/learn/architecture) | 区分宿主、客户端与服务端，提供工具、资源等协议能力 | 内置 Python 工具注册表还不是 MCP 客户端，需要连接、发现、授权和调用管理 |
| [Claude Code Hooks](https://code.claude.com/docs/en/hooks) | 可在生命周期事件上执行配置的动作 | Skills 负责流程指导，Hooks 负责确定时机的动作，两者应分别约束和记录 |

研究结论用于提出本文的产品建议。各节的完成标准、建设顺序和边界处理是针对本仓库的设计判断，不能理解成参考产品已实现完全相同的方案。
