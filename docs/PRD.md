## 1. 问题与目标

工具型 Agent 除了调用模型，还需要组织工具执行、上下文、任务状态、运行限制和结果交付。使用者需要知道任务运行到了哪里、产生了什么成果、为什么失败，并能在任务结束后追加要求继续修改，在中断后核对记录并通过普通消息接续，后续改进运行策略。

首批目标用户是需要委托小型代码修改的本地后端开发者。核心需求是：把真实仓库中的小修复交给 Agent，完成后检查代码 diff 和已有测试证据，再决定接收结果。项目也用于 Agent 岗位作品展示，但演示样例数量不作为产品优先级。自优化保留为后续研究方向，先以真实使用验证需求。

长期方向是在此基础上建设完整 Agent 工作台：用户可以先审阅计划，把目标拆成可跟踪任务，在后台持续执行并与 Agent 交互；按任务需要委派子 Agent 或组织团队，跨会话复用可维护的知识，最后审阅和采纳成果。远程多人、复杂多模态及平台生态是按需求选择的扩展，不要求为追求功能数量同时建设。

产品目标：

1. 能接收明确任务，在指定工作区自主调用工具并交付成果。
2. 执行过程可查看，失败有记录，运行受到明确限制。
3. 前端运行控制台与后端能力同步交付，后续同步扩展多轮任务交互、上下文管理、中断后接续和配置能力。
4. 能依据失败轨迹提出策略修改，经独立检查后采用或拒绝，并支持回滚。

技术栈、模型厂商及运行时复用方案记录于技术设计；本 PRD 约束产品能力，不要求复刻特定参考项目或从零重写全部组件。

## 2. 核心使用流程与交付物

基本流程：

打开电脑中的项目文件夹或最近项目 → 输入任务并发送 → 固定运行配置、所选目录与执行方式 → 模型决策 → 执行工具 → 回传结果并继续 → 生成成果 → 执行已配置的验收 → 展示结果与结束原因。未配置验收时明确保持未验收。

多轮任务交互流程（V0.2）：

查看本轮成果、测试与差异 → 追加要求 → 核对会话与代码状态 → 继承必要历史和已有代码修改 → 发起新一次运行 → 重新测试、生成差异 → 审阅或继续追加。

一次运行内部的多轮模型/工具调用由 Agent 自主推进；用户在运行结束后追加要求会产生新一次运行。两者分别记录，不能用已有工具循环或聊天历史展示代替多轮任务交互。

受限改进流程（按需质量改进，原 V0.3 目标）：

从真实任务记录定位一个可复现的问题 → 明确改进假设 → 提出一项允许范围内的候选修改 → 固定模型、起始代码、任务与预算，比较基线和候选 → 独立检查与回归 → 人工决定采用或拒绝，保留依据；采用后仍可回退。

先复用现有运行记录、配置快照、代码差异和项目测试；首版允许人工分析、人工修改或模型协助提出候选，不要求先建自动诊断服务、候选搜索系统或优化管理页面。无收益或发生退化时拒绝候选，也是完整的交付结果。

每次任务至少交付：运行标识、执行状态、验收状态、结束原因、执行轨迹和产物位置。产物可以是生成文件、代码修改或结构化结果，不要求每个任务都修改代码。

## 3. 用户故事与完整功能范围

以下覆盖任务管理、模型接入、执行循环、工具、环境、上下文、会话、轨迹、配置扩展和自优化十类功能。

1. **任务管理（V0.1，入口持续完善）**：作为使用者，我希望直接从电脑选择真实项目文件夹，或重新打开最近项目，输入任务后开始执行；首次使用不必修改 TOML 登记目录。系统识别 Git 根目录和普通文件夹，每次运行有独立标识。
2. **模型接入（V0.1）**：作为使用者，我希望配置一个支持工具调用的模型，以便在一次运行内完成多轮模型与工具交互；模型请求超时或失败时能得到明确记录。
3. **基础工具（V0.1）**：作为使用者，我希望 Agent 能读取、搜索、创建或修改文件，以及执行命令，以便完成真实操作；工具输入经过校验，结果保留错误与退出状态。
4. **自主执行（V0.1）**：作为使用者，我希望 Agent 根据工具结果继续决策，直至完成、失败或触发限制，以便减少逐步手动指挥。
5. **运行控制（V0.1）**：作为使用者，我希望设置轮次、调用和超时上限，并主动中断任务，以便控制失控循环和长时间运行。
6. **轨迹和成果（V0.1）**：作为使用者，我希望查看消息、工具参数与结果、耗时、结束原因和生成文件，以便理解过程和定位问题；重启后仍能读取已保存记录。
7. **结果验收（V0.1）**：作为使用者，我希望系统执行我预先配置的验收程序，以便区分“模型结束回答”和“产物符合要求”。
8. **上下文管理（V0.2）**：作为使用者，我希望系统加载项目说明、控制工具输出、按需读取内容并压缩旧历史，以便处理更长任务；原始轨迹仍可追溯。
9. **多轮任务交互（V0.2，优先）**：作为使用者，我希望在任务结束后继续发送要求，让 Agent 继承同一会话的必要历史和已有代码修改，再执行、测试并交付新的差异，以便逐步修正和完善结果；每次运行有独立预算、轨迹、验收与审阅记录，旧记录保持可查。
10. **中断后接续（V0.2）**：作为使用者，我希望重启后打开原会话并直接发送“继续”，复用已保存消息、工具记录与当前代码；未确认工具结果明确标记并先核对现场，不自动重放。当前不提供独立检查点入口或任意步骤精确恢复。
11. **前端运行控制台（V0.1，随工作流扩展）**：作为使用者，我希望通过新建、项目、会话及运行配置页面，提交任务、观察实时执行、取消运行并查看产物、验收与历史记录；这是必须交付的前端界面，详见 [前端需求](FRONTEND_REQUIREMENTS.md)。当前详情按结果、文件和诊断组织。后续新增用户可见能力时同步提供对应操作或展示；首版改进比较复用已有详情、产物与测试记录，独立优化管理页面按实际需要决定。
12. **可选执行隔离（后续扩展）**：作为使用者，我希望在批量回归、无人值守或多用户等场景下，明确选择 Docker 等受支持的隔离执行后端，限制命令的文件、网络与资源访问，并在取消和超时后核验清理。默认保持原目录与本机执行；容器能力不作为 V0.2 完成条件，按实际需求另行规划。
13. **运行配置与技能（V0.2）**：作为使用者，我希望选择模型、工具集合、技能及模型轮次、工具次数、总时限，并在每轮记录中查看实际配置与技能快照；上下文及内部限制由宿主 TOML 管理，以便核对执行条件。已有配置覆盖与手动技能继续复用；命名任务预设的增删改查和通用策略组件框架按重复使用需求另行规划，不作为 V0.2 完成条件。
14. **问题定位（按需质量改进，C14）**：作为使用者，我希望从当前版本的真实任务轨迹、差异和独立检查中定位一个可复现的问题，区分环境、任务说明、模型和 Harness 的影响，再形成有证据的改进假设。允许人工分析，自动跨记录归类与诊断服务后置。
15. **受限候选（按需质量改进，C14）**：作为使用者，我希望一次只验证一项允许范围内的提示词、工具说明或策略配置修改，记录基线、差异、来源轨迹和预期作用；候选可以人工编写或由模型协助提出，不要求先交付通用优化器。
16. **采用、拒绝与回退（按需质量改进，C14）**：作为使用者，我希望查看相同条件下基线与候选的结果、独立回归及决策理由，并能恢复原配置或源码。用源码标识、配置快照和结果记录追溯，不以完整的版本管理页面为前提。
17. **长期记忆与经验复用（长期范围，C09）**：作为使用者，我希望新会话按需使用以前确认的项目事实、偏好和带适用条件的经验，能够查看来源、纠正和删除；当前会话摘要只解决会话内接续。项目记忆首版已交付，其他扩展仍按实际需求规划。
18. **规划后执行（长期范围，C03）**：作为使用者，我希望先研究并修改方案，明确批准某一版本后再允许项目写入；界面显示待批准状态，后端实际约束动作，而不是仅靠模型遵循文字要求。
19. **结构化任务管理（长期范围，C04）**：作为使用者，我希望看到整体目标的工作项、依赖、负责人、阻塞与完成证据，并在失败或续轮后继续剩余工作；工作项与会话、单次运行分别记录。
20. **子 Agent 委派（长期范围，C07）**：作为使用者，我希望主 Agent 可以委派独立探索、审阅或受控实现，收到可核对的结果后统一交付，并能查看子执行、权限、用量和失败。
21. **Agent Teams（长期范围，C08）**：作为使用者，我希望多个成员围绕共享任务持续分工和通信，明确代码归属，在成员失联或冲突时可处理，最终按集成结果验收。
22. **后台工作（长期范围，C06）**：作为使用者，我希望排队或并行执行长任务，离开页面后仍可查看和停止；服务异常后明确恢复或人工接管，不能把日志读取冒充自动续跑。
23. **运行中协作（长期范围，C05）**：作为使用者，我希望回答 Agent 的问题、批准具体操作、补充约束或暂停工作；这些交互在刷新后可追溯，不能被旧回答或重复请求误触发。
24. **自动化工作（长期范围，C16）**：作为使用者，我希望按时间或外部事件触发已授权任务，管理重叠与重试，并仅在有意义的变化、完成、失败或需要处理时收到通知。
25. **工具与信息接入（按需求扩展，C10/C17）**：作为使用者，我希望按任务选择技能和外部工具、查官方资料或读取附件，能看清来源、权限及实际结果，不把命令执行能力等同完整工具生态。

### 4.1 前端控制台的交付范围

任务 API、SSE 事件订阅和前端运行控制台与后端功能同步开发和验收。基础控制台覆盖任务提交、实时详情、最终结果与产物、历史、运行配置和独立验收；后续新增用户可见能力同步提供对应操作。真实任务验收与首版改进比较优先复用已有页面和产物记录。页面、状态和 F01—F08 标准见 [前端需求](FRONTEND_REQUIREMENTS.md)，基础入口不依赖容器或恢复执行。

### 4.2 前后端同步迭代与完成条件

每次后端修改都检查接口、数据结构、配置、工具能力、状态、事件和错误语义是否影响前端；有影响时，同一迭代同步更新前端调用、类型、页面、交互、相关测试和文档。确实不影响前端的内部变更，在交付说明中写明原因。

版本或功能迭代的 Plan 必须列出后端变更、对应前端功能、共享契约及联动验收方式。验收从页面实际提交或操作开始，核对后端执行、事件展示、最终状态与产物；仅后端测试通过不能代表用户可见功能已交付。未接入的能力明确显示不可用或未验证，不使用静态占位数据冒充已完成的联动。

### 4.3 多轮任务交互的交付范围（V0.2）

该能力用于“第一次修改后补充要求、指出问题并继续调整”的基本使用闭环，优先于完整历史压缩等进阶能力实施。页面与 API 已交付本节的首版范围；实现和限制见 [多轮任务交互](MULTITURN_TASKS.md)，整体版本进度以 PROJECT.md 为准。

同一会话包含初次请求与后续追加要求；每条被接纳的请求发起一次独立运行，一次运行内部可有多轮模型与工具调用。各次运行分别固定配置、预算、指令快照和输入来源，保存模型/工具轨迹、结果、验收状态及对应代码差异，并记录所属会话和前序运行关系。旧运行的最终回答、测试结论、已保存事件和补丁不被覆盖。

详情页采用持续会话工作区：用户消息与Agent回答清晰分开，底部输入持续可用，回答支持受限Markdown与代码复制，真实工具/验收过程可折叠查看。发送新一轮不重建消息区域，查看旧轮只切换详情，发送始终追加最新轮；运行中允许编辑、禁止新提交。后续运行继承理解任务所需的原始要求、已有结论、必要工具证据和此前代码修改；先核对代码状态，再请求模型。代码项目的来源和旧轮次快照必须可追溯；Git 隔离首轮创建一个会话工作树，后续复用同一目录，各轮固定补丁、历史产物和验收，不重建目录或搬运旧补丁。个人普通目录持续在所选目录执行，逐轮保存独立证据。

前轮已有可信终态，或具有完整可核对的中断事件前缀且工作区可访问时，接受追加要求。中断后同样从原输入框发送“继续”或补充要求，产生独立新运行与新预算。同会话运行中保持串行限制，其他独立项目可以并发，提示等待或取消并保留输入；记录损坏、已结束运行清理不确定、代码已丢弃或工作区来源无法核对时，明确说明不能继续的原因。中断记录中的未知工具先核对后置状态，不把缺少结果解释为未执行。查看历史、刷新或重启服务不会自动发起新运行，也不重放旧工具。

追加要求后的新修改需要重新执行宿主登记的验收并生成本次代码差异，审阅重新等待用户决定。界面区分本轮测试与此前测试、本轮待审阅与此前审阅结论；原轮次通过或保留的决定不能代替新结果。多轮交互仍遵守已有输入预算，历史压缩已接入有来源的分层投影，仍超限时保留记录并明确停止；运行中插话、并行分支及任意步骤精确恢复另行安排。

| 编号 | 验收场景 | 可观察的通过条件 |
| --- | --- | --- |
| M01 | 完成后追加修改 | 页面先完成一次修改，再追加要求；后续运行理解前文并继承已有代码修改，产生可核对的新结果 |
| M02 | 各轮结果独立 | 每轮有独立运行标识、预算、事件、验收与差异；新一轮重新测试；仅隔离Git等待保留/丢弃，旧记录与结论可查且不被覆盖 |
| M03 | 刷新与服务重启 | 已结束会话和关联运行可重新读取，再次追加仍可核对已有代码；单纯读取不会启动执行或重放工具 |
| M04 | 运行中或重复提交 | 保持同会话串行；运行中、提交失败或重复提交有明确反馈并保留输入，不因重复请求执行两次修改 |
| M05 | 无法核对继续条件 | 记录损坏、已结束运行清理不确定、代码已丢弃或来源异常时给出可读原因；可核对的中断记录允许发送继续 |
| M06 | 输入预算不足 | 继承后按实际拟发送的消息及工具定义检查预算；压缩有来源，摘要调用如实计数；最终超限停止并保留记录与代码，未发出的请求不计数 |

### 4.4 真实代码任务验收（V0.2）

现有工作台已具备项目入口、多轮交互、工具执行、上下文管理、配置快照、测试与差异展示。2026-10-26 的首轮真实任务见 [历史验收](REAL_TASK_ACCEPTANCE.md)；2026-10-29 已按获批 G01 用当前实现完成本节范围的复验，见 [可靠性报告](RELIABILITY_ACCEPTANCE_20261029.md)。V0.2 按可信本地、允许人工消息接续的既定首版范围验收完成；失败及干预仍保留，不把功能完成等同模型自主交付质量已经稳定。

先复用现有页面、CLI、运行记录和项目测试，以少量实际任务形成可复查记录，不另建评测平台或统计看板。任务开始前固定需求、起始代码和依赖条件，优先使用已有测试与用户明确的验收条件；现有测试不足时，补充与需求对应、在比较前固定的独立检查。执行、验收和用户审阅分别记录，模型声称完成或自行运行测试都不能代替宿主检查。

记录任务要求、实际修改目录、源码状态、实际配置、运行标识、工具轨迹、代码差异、检查结果、人工干预、耗时及可取得的用量。供应商未返回的用量标记为未知；接入检查、固定响应的工程测试和真实模型任务分开标注，工程测试通过数量不作为代码任务成功率。

| R01 | 真实项目与修改目录 | 页面选择真实项目后，文件工具、命令和项目测试使用显示的同一实际目录；已有改动与本轮改动可核对，显式隔离时保留来源与基线 |
| R02 | 小修复与小功能 | 真实仓库的小修复与小功能均有通过独立检查、可供审阅的成果，逐项对应事先约定的需求并完成必要回归；失败尝试、未验证项和人工干预另行记录 |

本节先核对当前交付质量，发现的阻塞问题按具体失败单独修复并复验。关键证据缺失或存在阻断基本交付的未解决问题时，V0.2 不标记完成。只有出现可复现的问题与明确假设，才提出后续功能或策略改进 Plan；尚无证据时继续真实试用，不为了填满路线增加模块。

### 4.5 可选执行后端的后续边界

当前默认原目录与本机执行，仅面向可信本地单用户；工作目录设置和文件工具路径检查不构成操作系统命令沙箱。后续出现批量回归、无人值守、多用户或不可信代码执行需求时，应重新评估并先补足适用的执行隔离，不能仅扩大当前可信模式的使用范围。

Docker 后端另行提交 Plan，经批准后实施。工作区与执行环境分开选择；Docker 使用同一实际代码目录的明确挂载，可写挂载会修改宿主代码。Runner、模型调用、会话与事件保留在宿主；模型命令和项目测试进入所选容器，处理 Windows/Linux 路径与解释器差异。

首版候选范围保留固定 Linux/Python/pytest 镜像与提前准备的项目依赖、每轮一个容器、明确资源/网络/挂载限制及归属清理。Docker 或镜像不可用时在模型调用前提示，运行中依赖不足时明确失败；不静默改成本机。取消、超时和服务异常退出需要约定可核验的停止与遗留回收边界，旧轮代码、差异与产物保持。具体资源值、生命周期协议和异常验收在该轮 Plan 中确定，不在当前版本中视作已交付。

### 4.6 受限改进首版（V0.3）

本节保留原 V0.3 受限改进的范围及 I01—I05 验收标准，用于后续按需启动的质量改进。自 2026-11-02 起暂缓独立实验，不作为当前版本必需交付或 Permission 开发的前置条件。启动前须以当前版本证据确认问题仍影响交付，并形成可验证的原因假设；不能仅为补齐历史版本清单启动实验。实验次数、成本上限和停止条件由届时获批 Plan 确定，当前未授权任何真实模型比较运行。

从真实任务中选择一个影响交付的问题，先确认任务说明、检查程序和依赖环境是否正确，再判断 Harness 能否通过一项有边界的修改改善结果。问题可能涉及重复读取、工具参数、关键约束丢失或验证遗漏；这些只是候选方向，不预先认定需要新增对应系统。

首版候选只修改批准范围内的一项提示词、工具说明或上下文等策略配置。可以人工分析和修改，也可以由模型协助提出，再由人审阅。验收器、隐藏测试、数据划分、权限、密钥与宿主预算不可被候选修改；核心程序缺陷单独按功能修复 Plan 处理，不通过候选绕过限制。

比较时固定模型、任务、起始代码、依赖和预算，基线与候选分别从同一初始状态运行，保留结果及成本。首版可以在当前可信本地模式进行明确控制的比较；涉及不可信代码或超出该模式的场景时，先满足 4.5 节的执行隔离边界。已有配置快照加源码提交或文件指纹即可标识比较对象，不要求预设管理器、通用插件注册表或专门的优化页面。

| 编号 | 验收场景 | 可观察的通过条件 |
| --- | --- | --- |
| I01 | 问题与假设 | 原始轨迹和独立检查能支持一个可复现问题，说明候选预期改善的行为及失败判据 |
| I02 | 受限修改 | 候选差异可审阅，仅涉及事先允许的修改面；不修改验收、隐藏测试、权限和宿主预算 |
| I03 | 公平比较与回归 | 固定模型、起始代码、环境、任务与预算，保存基线和候选运行标识、独立检查、回归、人工干预及成本；候选不继承基线执行后的代码 |

## 5. V0.1 详细需求

### 5.1 输入与工具

输入包括任务描述、工作目录、运行配置，以及可选的验收入口。工作目录不存在、缺少必需配置或验收入口无效时，应在启动前给出可读错误。

基础工具覆盖：读取文件、搜索内容、创建或修改文件、执行命令。工具结果至少包含成功或失败、输出或错误；命令额外保留退出状态与超时信息。过长输出向模型返回有标记的截断内容，完整输出保存为可追溯记录；较大文件支持分段读取。

首版在用户指定的可信本地工作区运行。文件工具限制访问范围，命令设置工作目录、超时与清理逻辑。工作目录约束不等于命令沙箱；容器隔离调整为后续可选执行后端，当前可信本地模式不承诺防护恶意任务。首版仅支持普通前台命令，进程树清理采用本地平台的最佳努力机制；后台守护或脱离父进程的程序暂不支持。清理无法确认时明确记录未知或不完整状态，不报告完整清理成功。

### 5.2 执行与终止

模型生成的工具名称和参数需校验，不能因为单次格式错误直接破坏运行。工具错误作为观察结果返回模型；宿主配置错误和不可恢复异常应终止并记录原因。

支持最大模型轮次、最大工具调用数、单次模型请求超时、单次命令超时和总运行时长限制。模型请求重试有上限；产生副作用的工具不得盲目自动重试。用户中断后停止调度新工具，并清理正在运行的关联进程。

费用与 token 先做统计；缺失的供应商用量标记为未知，不记为零。精确费用预算和多任务调度留到后续版本。

### 5.3 执行状态与验收状态

执行状态与验收状态分别展示：

| 执行状态 | 含义 |
| --- | --- |
| 已创建 / 运行中 | 任务已登记，或正在调用模型与工具 |
| 执行完成 | 模型结束本轮任务，尚不能单独证明结果正确 |
| 执行失败 | 遇到不可恢复的模型、工具或宿主异常 |
| 已取消 | 用户主动中断或上游任务取消，分别记录来源 |
| 已超时 / 达到上限 | 超过时长、轮次或调用次数限制 |

验收状态为“未验证、通过、未通过、验收异常”。没有验收入口时保持未验证；只有执行完成且验收通过，才展示为任务成功。验收失败不能覆盖原始执行记录。验收程序也需设置超时、输出上限和中断清理，总体时限涵盖验收阶段。断言不满足显示未通过，启动失败或超时显示验收异常；执行已完成时保留原执行状态，另行记录验收异常原因。具体验收协议在技术设计中确定。

验收入口由使用者预先指定，由宿主调用，不由模型自行选择评分标准。验收程序与工作产物分开管理；V0.1 的可信本地模式不作为强安全隔离。

### 5.4 记录与示例任务

运行记录应保存任务输入、配置快照、模型与工具消息、工具结果、时间、用量、结束原因、验收结果及产物位置。不得保存明文密钥。中断前已完成的关键步骤应落盘；不承诺任意时刻崩溃都无损。

固定日志样例用于验证通用执行与独立验收。CSV 和目录清单可以作为后续回归素材，但不再作为近期必须交付的产品功能。

### 5.5 真实项目任务与代码审阅

用户打开本机 Git 根目录或最近项目；页面显示真实路径、分支、提交及未提交状态。默认直接在所选目录执行，工具、命令和测试使用同一目录，包含当前未提交改动。高级设置可明确改为隔离执行，此时才指定基线、建立独立工作树，不带入源目录未提交改动。已有预算、轨迹、取消及独立验收机制继续复用。

产物自动登记本轮新增、修改的文件，覆盖命令生成的报告及二进制；已有未修改文件和依赖缓存不作为新交付，删除只显示在差异中。收集不完整需单独提示，不能替代执行或验收结论。

项目测试为可选项，Git 项目可在项目页“项目设置”保存测试命令和秒级超时；保存只校验和登记，不运行命令。未配置时允许执行，结果保持未验收。普通文件夹也能在该面板保存项目名称和Python解释器，可在提交时选择宿主已登记的独立验收。宿主 TOML 可继续作为初始登记来源并配置源码搜索目录，不是打开真实项目的前置步骤。普通文件夹始终在所选目录执行；没有提交的 Git 项目可登记但不能启动代码任务。

终态后保存新增、修改、删除、重命名及二进制变更的证据。页面提供 diff、完整补丁下载、测试输出及审阅决定。保留只保留工作树和补丁，不自动提交或合并；丢弃须确认，仅移除已核验属于本任务的工作树，历史记录与补丁继续保留。审阅状态独立于执行和测试状态；测试通过不代表用户已接受修改。完整边界见 [代码任务与审阅](PROJECT_TASKS.md)。

离线确定性测试覆盖运行机制与异常路径；少量真实模型检查覆盖实际接入。历史测试结果与 F01—F08 页面证据集中在 [控制台验证记录](WEB_CONSOLE.md#7-已保留的验证证据)，最新交付范围见 [项目概览](../PROJECT.md)。真实项目额外验收源改动保留、基线固定、工作树测试导入、完整diff、保留/丢弃与重启读取；大规模数据集、统计显著性、多组对照和排行榜实验不属于 V0.1 验收。

## 7. 后续实现决策与自优化边界

技术设计按实际职责组织执行器、模型适配、工具执行、上下文、会话存储与运行服务；验收器与产物评分保持独立。受限改进首版复用已有记录和验收，新增模块由具体问题及获批切片决定，不以搭建通用优化器为前提。

V0.2 中断后接续复用现有多轮输入、持久事件、代码副本与Runner，不新增独立恢复按钮。来源事件序号与消息摘要在模型调用前重新核对；中断源代码只在明确提交时捕获，表示接续时现场。对“工具可能已执行、结果尚未记录”的情况，先检查后置状态或标记待核对，不直接重放任意命令。网页事件订阅与任务生命周期解耦，客户端断开连接不等于取消任务。

模型执行循环已把命令退出状态、错误和输出回传给模型，可在同一运行中继续修改和重试。公开项目测试现可明确开启失败后的有限自动修复，完整边界见第15节；独立验收仍只检查一次，其输出不作为模型修复反馈。公开测试反馈不是用户追加要求，也不授予额外工具或预算。

受限改进按第 0.3 节的触发条件启动，获批后按第 4.6 节完成候选比较与人工决策。候选输入只使用允许的任务与反馈，不接触最终隐藏检查；候选与基线的代码及配置分别固定，记录来源、差异、结果和拒绝原因。命名预设、通用策略框架、自动诊断与经验库均不作为比较的前置依赖。

通过少量回归样例属于功能检查。宣称“能力提升”之前，还需独立的未见任务验证；开发阶段反复使用的验证结果不得当作最终泛化分数。

| D05 | 目录被替换/删除时拒绝续聊；原目录没有工作树保留/丢弃按钮，Git已有暂存和提交不被自动改写 |

实现和限额见 [打开本机项目](LOCAL_PROJECTS.md)。


## 13. 局部代码编辑（V0.2）

Agent 修改已有文件时，可使用单文件、单片段的 edit_file 工具：先读取当前内容取得完整文件指纹，再提交旧片段、新片段和预期指纹。只有当前版本一致且旧片段唯一匹配时才写入；空的新片段表示删除。该能力补充已有的读取、搜索、创建文件与命令工具。

| 编号 | 验收内容 |
| --- | --- |
| E01 | 唯一片段被替换，无关内容、中文、BOM、CRLF 和原权限位保持 |
| E02 | 找不到原文、匹配多处（含重叠）或无实际修改时，返回明确错误，原文件不变 |
| E03 | 用户在读取后或临时文件写入期间改变目标时拒绝提交；重新读取后可继续，保留外部编辑 |
| E04 | 原文件与结果受文件写入字节预算限制；越界、运行记录、非普通文件及不支持编码均明确拒绝 |
| E05 | 配置页启用后真实任务使用该工具，执行过程显示参数与结果；两轮修改、项目测试、重启及旧证据保持通过 |

编辑不自动执行批量替换或格式化；出现冲突时不自动降级到整文件覆盖。内容指纹是乐观并发核验，仍适用可信本地单用户边界。完整参数、错误与预算见 [技术设计第6节](TECH_DESIGN_V0.1.md#6-文件与命令工具及本地执行边界)。

## 14. 项目执行配置与会话工作树

项目页“项目设置”可保存 Python 解释器；Git 项目同时保存公开测试入口。原目录仍为默认。隔离工作树属于会话，多轮及重启后沿用同一目录；运行证据按轮固定。

| 编号 | 验收内容 |
| --- | --- |
| X01 | `**/*.py` 同时命中根目录和嵌套 Python 文件，`nested/**/*.py` 包含直属文件；既有搜索限制保持 |
| X02 | 保存解释器不执行程序；模型命令和裸 Python 项目测试采用同一配置，重启仍保留 |
| X03 | 无效显式入口在模型前拒绝；PATH 无 Python 不阻止其他明确程序入口 |
| X04 | Git 隔离连续三轮及重启后目录路径和身份相同，原仓库与两轮间手动文件保持 |
| X05 | 旧轮没有目录管理操作；后续修改及最终丢弃后，历史补丁和已保存产物字节不变 |
| X06 | 后续准备失败不调用模型、不删除共享目录、不改写旧证据；恢复配置后可继续 |

直接替换逐轮派生逻辑，不保留旧接口别名或迁移分支；不自动删除既有记录和目录，无法核对的旧隔离结构明确提示。

项目 python_executable 为显式解释器，空白按 PATH 查找；模型命令和项目验收的裸 python/python3 共用当轮选择，明确程序路径及 uv 等其他入口原样执行。相对路径按实际工作区解释，不自动创建环境或安装依赖。

只有最新轮可保留或丢弃共享工作树，旧轮只读，运行中拒绝删除。前轮 kept 不代表新轮已经接受；丢弃后不能继续，但已保存历史文件和补丁仍可下载。不自动提交或合并。新轮尚未启动时准备失败，仅回退会话管理状态，已有目录保持。

## 15. 公开项目测试失败后的自动修复

用户可在已保存项目测试后，明确开启“测试失败自动修复”，默认关闭。模型完成一次回答后由Runner运行公开测试；正常断言失败且进程清理安全时，最多追加两次修复及重测。使用同一运行、代码目录、消息、指令与压缩状态，全部模型/工具/检查共用原模型次数、工具次数和总时限。独立或隐藏检查不得回传给模型，检查入口由宿主固定。

每次检查保留独立输出和结论。修复开始后，当前代码恢复未验收，旧检查只作为历史；最终结果必须对应最后代码。公开反馈标记为宿主数据，不作为新的用户要求或工具授权。运行结束前统一固化文件与唯一终态；重启只读取历史，继续执行需要用户明确追加要求。

| 编号 | 可观察的验收条件 |
| --- | --- |
| AR01 | 默认关闭；仅已保存的公开项目测试可开启，缺失或独立检查在模型前拒绝 |
| AR02 | 首次失败后沿用原会话修复并重测，通过后停止；最多两次修复、三次实际检查 |
| AR03 | 修复中仍受原总预算约束；没有新检查时不以旧通过或失败冒充当前结果 |
| AR04 | 启动错误、异常退出、超时、输出超限、清理异常和取消均停止；不自动重试这些异常 |
| AR05 | 页面展示修复阶段及次数、当前结果、历史失败与各次原始输出；开关随本轮配置冻结 |
| AR06 | 原目录与Git隔离均可修复；最终差异和产物对应最终代码，历史轮次及来源文件不被改写 |
| AR07 | 后续用户轮次默认继承开关，也可更改；结果未知的请求重试使用原载荷，不改变已发授权 |
| AR08 | 修复中断后重启可查看已保存检查，读取不重放；用户明确继续时继承必要反馈和当前代码 |

## 16. Agent 主动规划与人机决策

本轮以完整的“研究 → 提问 → 方案版本 → 用户决定 → 执行 → 验收”为交付单位。用户可选择先规划；自动模式下 Agent 应对复杂功能、架构调整、重大选择及范围变化主动调用 `enter_plan_mode`。需要确定性先批准的宿主使用 `planning_policy = "required"`，网页不能覆盖。默认自动判断不承诺对任意自然语言要求完美识别，不能替代强制策略。

规划阶段只开放受控读取、目录发现和决策工具；写入、局部编辑及所有命令由后端拒绝，项目检查同样不执行。方案包含目标架构、范围、步骤与前后端影响及验收；批准绑定当前请求、版本、实际目录和目录对象身份。普通文字不能代替结构化批准，新方案须重新审阅。批准范围内自主完成实现、测试及必要修复。

问题或方案提交后，本 Run 以 `waiting_input` 保存并释放槽位；回答/批准通过现有幂等追加协议建立新 Run，预算按新轮计算。重启读取不自动执行，中断前缀只继承已保存事实；拒绝方案、取消问题不调用模型或检查。协议、CLI边界及证据见 [主动规划](PLANNING.md)。

| 编号 | 完成条件 |
| --- | --- |
| PM01 | 用户可选择先规划，Agent可在自动任务中主动进入规划；宿主required策略在第一个模型动作前生效 |
| PM02 | 规划写文件、局部编辑和命令执行均被后端拒绝；目录发现无需Shell，宿主测试不执行 |
| PM03 | Agent能主动提交关键问题，页面提供建议答案和自由输入；等待时后续同批工具不执行 |
| PM04 | 计划保存目标架构、范围、步骤、验收、版本和工作区；刷新和重启保持，可回看历史；当前和历史版本可导出 Markdown，网页与桌面共用附件下载链路，导出不改变批准或触发执行 |
| PM05 | 批准必须匹配当前请求与版本；旧方案、旧问题、错误动作及替换的工作区拒绝，不由模型自行授权 |
| PM06 | 批准后继承历史与同一工作区执行、测试和交付；原目录与隔离会话均联通，旧证据保持 |
| PM07 | 修改产生新版；拒绝计划或取消问题只保存决定；迟到回答、重复批准和网络重试不重复执行 |
| PM08 | 步骤工具只更新当前批准版本的已有步骤，不改正文；模型进度不冒充实际测试通过；上下文默认装载当前版本及最新进度，压缩后重新注入；旧版本、决定原文通过只读分页工具回读，完整磁盘事实不删减 |
| PM09 | 前端区分等待回答、待批准、规划结束和开发结果；会话内计划块待批准展开，执行时收起正文并显示步骤进度，长文不挤占审批操作，修改表单按需展开；历史检查器只读，手机布局与异常恢复有验收记录 |

运行中任意纠偏、通用动作审批、暂停恢复、Agent Tasks、并发队列和团队协作不属于本轮批准范围，继续保留在能力全景。

| PP07 | 纯动作审批接续沿用剩余模型/工具/活动时间、修复次数与已知Token记录；不重复计算原调用，不借审批增加修复次数 |
| PP08 | 刷新、重启和历史读取不触发执行；取消排队撤销许可；过期尚未执行明确失效，已开始而结果不明需核对，不自动重放 |
| PP09 | 桌面/Web页面展示实际权限、具体目标及修改内容、命令、决定和历史；后台中心区分等待原因，手机布局及整条HTTP/Runner链路有验证证据 |

当前仍是可信本机单用户执行，不提供操作系统进程/网络沙箱、命令前缀白名单、永久授权或自动审批模型。写入型子 Agent 及成果集成见[开发协议](DEVELOPMENT_SUBAGENTS.md)，工作树隔离不等同于命令沙箱。CLI执行相同权限判定，等待返回4；完整人工审批在桌面/Web会话提供。本轮不改变G02—G04的完成事实，不把功能验收等同于模型质量提升。

## 21. 本机长任务与运行中协作（C06＋C05）

2026-11-04 按用户批准 Plan 实现；目标、命令与消息状态、暂停预算、父子接续及 HTTP/桌面/Web 验收集中在[长任务协议](LONG_RUNNING.md)。同步和后台命令共用执行机制；未收拢命令不能越过独立检查或成果快照。后台接纳不等于成功，未知结果不自动重放；不改变既有权限和桌面退出边界。

## 22. 可审核生命周期 Hooks（C10）

宿主与项目通过统一 TOML 声明事件、匹配条件、命令、作用角色、超时和失败策略；桌面/Web 提供定义与源码审核、启停、具体动作批准及当轮记录。支持工具执行前后、后台命令真正结束、摘要压缩前后、父宿主子执行起止、运行开始及完成检查。详细协议见 [Hooks](HOOKS.md)。

- H01：未审核脚本不执行；配置或入口内容变化后重新审核，历史保留旧定义。
- H02：审核与具体动作许可分别校验；Hook 不能绕过权限、Plan、只读角色、预算和工作区归属。
- H03：前置拒绝没有原工具副作用；后处理故障保留原回执，不能伪装成原动作未执行。
- H04：审批及安全暂停保存阶段与待处理事件；重启不重复执行已完成脚本、原工具或未知命令。
- H05：后台句柄与真正结束分开；压缩、父子事件和有限 Stop 续跑受原预算约束。
- H06：所有外部脚本在最终独立验收及产物固定前完成；Hook 通过不能代替验收。
- H07：通过页面审核、真实模型写入、格式化、宿主检查、差异与历史记录的完整链路验收。


## 23. 跨项目后台调度与安全恢复（C06＋C15）

2026-11-05 按批准 Plan 将主运行从全局单槽改为有资源归属的本机并发。用户可以同时推进独立项目，后台查看活动、排队、需要处理和结束结果，定向停止一项而不影响另一项。同会话、同 Git 公共目录、父子目录及宿主声明的共享资源组仍串行。详细配置、接口和验收见[调度协议](SCHEDULING.md)。
