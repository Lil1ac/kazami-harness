62 个提前通过的运行里，有 38 个最终留下了题面以外的文件，另 24 个最终只改了指定目标。因此，即使提前拿到最终答复，交付是否符合用户限定的修改范围也要单独检查。

## 建议的收尾策略

先在这类只开放文件工具、由宿主验收的任务上试验**按剩余预算提示，保留真实修复机会**。沿用现有宿主的写入回执、文件指纹与停止原因。原专项明确关闭 root_handoff，而现有根段机制在满足条件后会在最后一轮收回工具。候选策略单独用一次轻量提示干预，本试验两组都保留原工具集合与原权限。

- 从还剩 3 轮开始，给模型一条简短的运行事实摘要，列出剩余轮数、允许修改的目标、与当前文件哈希相符的最近写入，以及是否有真实自测回执。只开放文件工具时明确告知独立验收由宿主完成，此时无需创建空间内测试脚本。模型按当前事实选择继续修改或给出最终答复。
- 还剩 1 轮时，如果修改已完成，引导直接说明改了什么、哪些检查实际执行、哪些仍待宿主验收。如果仍有明确未完成的修改，保留这轮工具权限。若该轮用于编辑，按原规约记录产物和耗尽状态。待审批、版本冲突、越范围修改及缺少执行回执须如实呈现。清空自测文件也会留下额外路径。
- 运行时只引用该 Run 已有的真实文件和工具事实。独立评分结果对两组始终隐藏，末轮的选择由模型作出。前端沿用 Run 详情，同时显示提醒轮次、当前修改范围与自测状态，方便复核。工具权限、评分方式、轮次与费用账本保持同一口径。
